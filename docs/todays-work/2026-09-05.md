# Part 1 — Open problems (due 2026-09-07)

Found reviewing `f48049f` (server target) and `38e731a` (null-renderer fixes).
Neither commit is wrong; these are three places where a stated guarantee is
weaker than its statement.

## P1 — `gpu_null.cpp`'s equivalence is unchecked, in a comment claiming it is checked

**Severity: medium. This is the axiom-5 hazard with no structural defence.**

[`src/render/gpu_null.cpp`](../../src/render/gpu_null.cpp) line 14 says:

> That equivalence is the property worth protecting, and it is asserted rather
> than asserted-in-prose: tests/gpu_seam_test.cpp §1 runs against the real gpu.cpp
> with no device and expects precisely the results below. A server build running
> that section must produce the same output, which is what makes "the headless
> build and the headless path agree" checkable instead of hopeful.

`gpu_seam_test` is registered once — `engine_test(gpu_seam_test)`, which links
`engine_runtime` and therefore the real `gpu.cpp`. The only target linking
`engine_runtime_server` is `server_link_probe`, which never calls a `gpu::`
function. **No build compiles or runs §1 against `gpu_null.cpp`.**

Why it matters beyond the comment: the linker catches a *missing* function — that
is real, and it is why this design is sound structurally. It cannot catch a
*different answer*. `NullRenderer` is immune to this by construction (pure
virtuals; adding one is a compile error). `gpu_null.cpp` is eight free functions
matched to their twins by name alone, with nothing tying the return values
together. Change `gpu.cpp`'s no-device answer for `blobSize` or
`textureFormatSupported` and the two builds silently disagree.

**Fix:** a second test target compiling `gpu_seam_test.cpp` against
`engine_runtime_server`, with an `#if ENGINE_SERVER_BUILD` return after §1 (which
is already self-contained and device-free — it ends at `initTestDevice()`).
Handful of CMake lines. Then the sentence is true.

- [ ] Add `gpu_seam_test_server` target + `add_test`
- [ ] Verify by mutation: change one return in `gpu_null.cpp`, watch it fail

## P2 — the server binary links all of Assimp

**Severity: medium. Correctness unaffected; it voids one of step B's two stated benefits.**

`f48049f` claims:

> A third condition keeps source importers out: a server reads cooked binaries
> only, which is the posture `ENGINE_WITH_SOURCE_IMPORTERS=OFF` already describes,
> applied to one target instead of the whole tree.

True of the translation units, false of the dependency:

```
nm build/server_link_probe | grep -ci assimp   →  4278
  3286 local text + 315 global text            =  3601 symbols of real code
  including 46 Assimp::Importer symbols
libassimpd.a                                   →  65 MB
```

`ENGINE_SERVER_EXCLUDED` can only remove entries from **`engine_runtime`'s**
source list. Assimp arrives from the other direction: `src/CMakeLists.txt:140`
does `target_link_libraries(engine_core PUBLIC assimp)` under
`ENGINE_WITH_SOURCE_IMPORTERS` (default ON), and `engine_runtime_server` links
`engine_core` PUBLIC. The cooker stack lives in `engine_core` too, so the server
target's exclusion list cannot reach it.

Nothing calls it — `runtime_boot.cpp:191` compiles the registration out, and 0
bgfx symbols is still 0. What this hits is the specific value claimed for step B:
*binary size, container image size*. Assimp is plausibly the largest single
contributor to the 5.3 MB of `__text` in that probe.

**Two honest options, pick one:**

- [ ] **Split the cooker sources out of `engine_core`** so a server can link a
      cook-free core. This is the real fix — a dedicated server has no business
      carrying a mesh cooker either — and it is the same shape as the split that
      made this target possible in the first place.
- [ ] **Or drop the size claim** and rest step B on the dependency argument (no
      libX11, no Metal, starts on a headless box), which is fully delivered and is
      the stronger argument regardless.

# Part 2 — Architectural audit: what is incomplete

Not a list of missing features — [`../plans/aaa-gap-analysis.md`](../plans/aaa-gap-analysis.md)
already does that, honestly, and this does not restate it. This is about
incompleteness of a different kind: **places where the architecture makes a
promise that the implementation only half-keeps.** Those are the ones that get
more expensive with time, because callers are written against the promise.

## 2.1 The shape of the tree, stated in numbers

Lines of C++ per subsystem (excluding embedded font/shader blobs, which are
35,722 of `src/editor`'s raw total and would otherwise make it look like the
biggest thing here):

| subsystem | LOC | tier |
|---|---:|---|
| `modules/assetlib` | 20,704 | hardened |
| `src/runtime` | 11,172 | hardened |
| `src/editor` | 8,565 | prototype |
| `src/assets` | 7,011 | hardened |
| `src/render` | 6,792 | working |
| `src/core` | 2,951 | hardened |
| `src/tools` | 2,476 | — (no `info.md`) |
| `src/plugins` | 1,450 | working |
| `src/animation` | 1,370 | hardened |
| `src/scene` | 1,077 | hardened |
| `src/audio` | 900 | working |
| `src/components` | 516 | hardened |
| **`src/systems`** | **374** | working |
| **`modules/net`** | **89** | prototype |

**The two bold rows are the finding.** `src/systems` is the gameplay layer and it
contains one system. `modules/net` is a toolchain seam with no transport behind
it. Together they are 463 lines against roughly 65,000 lines of engine.

This is not a criticism — it is the deliberate inversion `aaa-gap-analysis.md` §0
describes, and it is the right inversion. But it means **the engine has never been
exercised by the thing it is for.** Every architectural claim below is currently
validated by tests and by the editor, not by a game.

## 2.2 Nine subsystems are `hardened`. The middle layer is where the gaps are.

Current tiers, 22 `info.md` files, 0 doctor errors:

- **hardened (9):** `assetlib`, `animation`, `assets`, `components`, `core`,
  `core/memory`, `runtime`, `runtime/jobs`, `scene`
- **working (11):** `render`, `render/world`, `render/diag`, `render/shader`,
  `audio`, `systems`, `plugins`, `project`, `packaging`, and two cookers
- **prototype (2):** `editor`, `net`

The audit's ordering principle — *hardening propagates downward* — has now been
carried through the bottom two layers. What remains at `working` and matters is
**`src/render` (11 dependents)** and **`src/render/world` (4)**. Everything else
still at `working` has few or no dependents, so its tier costs little.

`src/tools` has **no `info.md` at all** and 2,476 LOC, which is the same
invisibility `src/audio` had before 2026-08-28.

## 2.3 The incompleteness that actually compounds

Four places where the promise is ahead of the implementation. Ordered by how
expensive the gap gets if left.

### (a) "Swappable" is true at three seams and false at the one that matters

Seams that exist and work: `IPlatform` (glfw / sdl3 / headless),
`IRenderPipeline` (and since G1b, declarable with no graphics API in scope),
`IRenderer` (real / null). Plus `IEnginePlugin`, `IInputSource`,
`IProfilerChannel`, and the three script services.

The seam that does not exist: **the graphics backend.** There is exactly one, it
is bgfx, and `swappability.md` §3 is explicit that the cost is not dispatch but
the *semantic floor* — no bindless, a per-draw uniform model you cannot opt out
of, a 4,096-draw ceiling. G2–G4 are the work that closes this and none of it is
started.

So the honest statement is: *the engine is swappable everywhere it has already
been swapped, and untested everywhere it has not.* `NullRenderer` is a real
second implementation of `IRenderer` and proved the seam. There is no second
`IRenderPipeline` and no second backend, so those two seams are still claims.

### (b) The null twins have no structural protection (P1 generalised)

Three null implementations now carry the server build: `NullRenderer`,
`gpu_null.cpp`, `window_ops_null.cpp`. They have *different* degrees of safety
and that difference is not written down anywhere:

| twin | protects against missing | protects against divergent | why |
|---|---|---|---|
| `NullRenderer` | ✅ compile error | ✅ n/a | pure virtual; a do-nothing impl has no answers to diverge |
| `window_ops_null.cpp` | ✅ duplicate-symbol | ⚠️ partial | `window_ops.h` writes the null-handle contract down, so the impl is derived from a spec |
| `gpu_null.cpp` | ✅ link error | ❌ **nothing** | free functions matched by name; return values untied |

The pattern to adopt is `window_ops.h`'s: **specify the null answer in the header
that declares the function**, so the twin is derived from a specification rather
than from reading its sibling. P1's test is the cheaper fix; this is the
structural one.

### (c) The headless story is complete; the *server* story has barely started

G1 is closed and it delivered exactly what it promised. But "can run without a
GPU" and "is a dedicated server" are different claims, and only the first is true:

- No transport (`modules/net`, 89 LOC, no protocol)
- No replication, prediction, rollback or authority model
- `window_ops_null.cpp`'s own header states the limit: it makes a server *link*,
  it does not make network-driven input work
- No cook-time content exclusion — which `f48049f` correctly identifies as the
  largest server win and correctly places in the cooker, not the renderer

The risk here is momentum: G1c step B is satisfying and finished, and the next
step toward an actual server is much larger and lives in a different subsystem.

### (d) `src/systems` is the untested assumption underneath everything

One system, 374 lines. Every claim about the ECS, the job system, the component
ABI and the plugin ABI is currently validated by synthetic tests. The stress
lanes are good and they are not the same thing as a gameplay layer that pushes
back on the design.

This is the cheapest thing on this page to be wrong about and the most expensive
to discover late.

# Part 3 — Goals scorecard

Each goal is a capability someone would reasonably expect of this engine.
Sub-boxes are what that goal actually requires. **A checked box means it exists
and something enforces it**, not that it is planned.

- [x] `runtime.h` does not *reach* a graphics API transitively (`headless_include_probe`, gating)

## The one-line summary

**The foundation is done and the two ends are empty.** Everything from the memory
allocator up to the plugin ABI is `hardened` and machine-enforced; the renderer
below it is one backend behind an abstraction whose floor is known and low; and
the gameplay and networking layers above it are 463 lines combined. The next
decision that actually matters is **G0a** — the spike that tells you whether the
renderer programme is worth a year — and nothing in Part 1 should take more than
the two days allotted.
