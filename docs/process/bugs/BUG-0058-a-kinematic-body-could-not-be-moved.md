## BUG-0058 — a kinematic body could not be moved
- found:     2026-09-09
- status:    fixed
- class:     logic
- where:     src/plugins/jolt_plugin.h
- symptom:   setting `Transform.position` on an entity with a `PhysicsBodyType::Kinematic` `RigidBody` moved nothing, and the written value was gone by the end of the frame. No error, no warning, no log. Every moving platform, lift, door, elevator and swinging hazard was unbuildable — the whole category of content kinematic bodies exist for — and the failure presented as "my platform does not move", which reads like a content mistake rather than an engine one.
- cause:     NOTHING IN THE TREE EVER DROVE A KINEMATIC POSE. A kinematic body's pose is authoritative in Jolt and only changes when the host sets it; `MoveKinematic` appeared nowhere, and `SetPositionAndRotation` was likewise never called. `spawnBody` placed the body once at the entity's world transform and it stayed there for the session. Worse than inert: `writeBackTransforms` skipped only `Static`, so every step copied the body's unmoving pose back over `Transform` — the gameplay write was not ignored, it was ERASED, which is why nothing downstream could observe that a write had been attempted.
- pinned-by: tests/physics_authority_test.cpp
- lane:      unit
- proof:     `pushEcsToPhysics` runs once per Jolt SUBSTEP inside `onPhysicsStep` and drives each kinematic body to the entity's WORLD pose via `bi.MoveKinematic(id, pos, rot, kFixedDt)`. Per substep rather than per call, because MoveKinematic reaches its target by setting a velocity over the substep's dt: pushed once and stepped four times, the body would arrive and then keep going, overshooting by three substeps. Re-targeting each substep drives the velocity to zero on arrival. MoveKinematic and not `SetPosition` because the implied velocity is the point — it is what pushes dynamic bodies riding the platform. `writeBackTransforms` now returns for anything that is not `Dynamic`, making kinematic GAMEPLAY-OWNED in both directions. Mutation: commenting out the `pushEcsToPhysics` call fails 2 assertions (the platform never reaches x=5, and the character rotation of BUG-0059 never arrives); restoring the write-back fails the bit-identity assertion.
- note:      THE AUTHORITY TABLE IN THE PLAN WAS WRONG ABOUT THIS, and implementing it is what showed why. It listed Kinematic alongside Dynamic as physics-owned for position and rotation. But a kinematic body is one whose pose gameplay decides — that is the definition — so writing the physics pose back is a round trip through a velocity integration that does not land exactly on its target. Measured: the Transform gameplay set to exactly 5.0 comes back as 4.99999952. Small, and it accumulates, and it means gameplay's own value is not the value it reads. The test asserts BIT-IDENTITY rather than a tolerance for exactly this reason — a 1e-3 tolerance passes with the defect restored, which would have made the assertion a decoration.
