## BUG-0052 — unloading a shared mesh destroyed it for everyone
- found:     2026-09-06
- status:    fixed
- class:     memory
- where:     src/runtime/services/asset_service.cpp
- symptom:   an entity drawing the wrong geometry after any caller unloaded a mesh another caller shared. No crash and no log — `AssetRegistry::removeMesh` pushes the slot onto a free list with no generation counter, so the next `addMesh` pops it and the surviving holder reads a live `Mesh` that is simply the wrong one. Identical presentation to BUG-0051, one resource type over.
- cause:     `unloadMesh` ended in an unconditional `return m_meshes.removeMesh(h);` for a resource `m_loadedMeshes` dedups by path WITHOUT a refcount. The cache-hit path in `loadMesh` returns `it->second.h` to every subsequent caller, so N loads of one .cmesh hand N callers the same handle, and the first unload destroyed it for all of them. Reachable from Lua as `assets.unloadMesh`. This is BUG-0051's exact shape and it sat about twenty lines above the `unloadTexture` that BUG-0051 fixed, in the same file, in the same week — the texture fix's reasoning transferred verbatim and was not transferred.
- pinned-by: tests/mesh_ownership_test.cpp
- lane:      unit
- proof:     `MeshResidency` gains `refs`, counting loadMesh/unloadMesh PAIRS: 1 at the load that creates the entry, +1 at each cache hit that RETURNS the shared handle, -1 per unload, destroyed at 0. The increment sits at each `return` rather than once at the top of the hit block, because the skinned fall-through does not hand back that handle — it drops through to a full load that installs a different one, so a count taken before the branch would attach that caller to a handle it never receives. (The first version of this fix went further and said the superseded entry's own count "would be discarded with it" — accurate as a description of the code, and the reason for the follow-up below.) The test drives the real `loadMesh`/`unloadMesh` and asserts the second holder still resolves through `AssetRegistry::getMesh` after the first unloads. Mutation: restoring the unconditional `removeMesh` fails three assertions — the mesh is no longer resident for the second holder, its texture drops to `refs == 0` while a live material points at it, and the final unload reports failure. The test labels its own limit: section 3 (reload is still a cache hit) passes under the mutation too, because the destroyed slot goes on the free list and the reload pops the same id back with a different mesh in it — the silence that makes this class expensive is precisely what no assertion in that section can see.
- note:      TWO liveness mechanisms now coexist for meshes and the distinction is deliberate. `refs` gates the explicit unload path only. `evictOverBudget` keeps deciding from the caller's ECS in-use scan, because a mesh is referenced by components the cache cannot see and every cached entry has `refs >= 1` by construction — gating eviction on the count would evict nothing, ever. Textures need no such scan precisely because their refcount is complete. Fixing this also exposed that `evictOverBudget` erased mesh entries without releasing their `textureKeys`, so an evicted mesh pinned its textures at `refs > 0` forever and the texture budget reclaimed nothing on the automatic path — the same leak `unloadMesh` had just been fixed for, on the other path a mesh entry can die. Both now release.
- follow-up: 2026-09-07 — THE FIX DID NOT COVER THE SKINNED PATH, and that path is not an edge case. `loadMesh` only returns a cached handle when the caller wants no skin; a caller passing `outSkin` falls through to a full load ending in `m_loadedMeshes[key] = {...}`, an overwrite. `AssetService::m_skeletons` is declared in the header and assigned nowhere in the tree, so the `!m_skeletons` disjunct guarding that fall-through is ALWAYS true and every skinned load past the first took it. The superseded entry was the only record of two things: the texture references its own load acquired — never given back, so the texture budget could never reclaim them, the exact failure this commit had just fixed for the sync path — and its `refs`, so when more than one caller held the superseded handle each reached the unconditional `removeMesh` through the no-entry path and destroyed it more than once. BUG-0052 surviving inside the fix for BUG-0052. Fixed by re-keying the superseded entry to `"<path>\n#superseded:<n>"` instead of letting it be overwritten: `unloadMesh` and `evictOverBudget` both match entries by HANDLE and walk the whole map, so old holders still find it, still decrement, and the last still releases its textures and its registry slot — while nothing that looks up by path can reach it, which is what makes the new entry the live one. Pinned by `mesh_ownership_test.cpp` §6 (the leak) and §7 (the double destroy); mutation removing the re-key fails five assertions across both. §6's third assertion is labelled in-source as non-discriminating: it passes under the mutation because a handle with no entry falls to the unconditional `removeMesh` and reports success from there.
- open:      `m_skeletons` is a member nothing wires, so the branch that reads as a live condition is dead. Either the skinned streaming path that was meant to assign it is missing, or the disjunct should say plainly that skinned loads never dedup. Not decided here.
