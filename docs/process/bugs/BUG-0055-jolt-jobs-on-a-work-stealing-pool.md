## BUG-0055 — Jolt jobs on a general work-stealing pool: a use-after-free and a re-entrancy assert
- found:     2026-09-08
- status:    open
- class:     threading
- where:     src/plugins/jolt_jobs_adapter.h
- symptom:   a headless process running physics traps under CPU contention — `determinism_gate_test` under `ctest -j4`, roughly one run in ten. It needs load; 48 consecutive standalone runs are clean. Both traps land on the MAIN thread inside `JoltPlugin::onSimulationStop` or inside a Jolt job the main thread is executing, and in a Debug build they surface as Jolt's own asserts. With asserts compiled out the first is a silent use-after-free.
- cause:     `JoltJobsAdapter::QueueJob` hands a raw `Job*` to `jobs::run` FIRE AND FORGET, and Jolt's job system is designed around a pool it owns. Two distinct consequences, and lldb backtraces separate them. **(a) FIXED HERE:** nothing waited for queued jobs, so destroying the adapter freed the `FixedSizeFreeList` pages a still-queued lambda was about to run `job->Execute(); job->Release();` against — caught by `JPH_ASSERT(mNumFreeObjects == mNumPages * mPageSize)` in `~FixedSizeFreeList`, reached from `onSimulationStop`. **(b) STILL OPEN:** `JPH::BodyAccess::Grant` asserts `velocity == EAccess::ReadWrite` in `JobFindCollisions`, on the main thread, called from `TrySpawnJobFindCollisions`'s lambda. `BodyAccess` keeps its access tokens in THREAD-LOCAL state, which assumes a thread runs Jolt jobs with well-defined nesting. The engine pool is work-stealing and the barrier wait executes queued jobs on the waiting thread (documented in the adapter header), so a `physics.job` can begin on a thread already inside another Jolt job. The nested `Grant` then sees state its predecessor has not restored.
- lane:      determinism
- note:      HALF FIXED, and the halves are recorded separately because they need different fixes. (a) is closed: the adapter counts outstanding queued jobs and its destructor waits for zero before the free list dies, with a 5-second deadline that aborts loudly rather than corrupting. That alone took the failure rate from roughly three runs in eight to one in ten. (b) is a design question, not a patch: running Jolt's jobs on a general-purpose stealing pool is what makes its thread-local access tracking unsound, and the options are a non-stealing execution path for physics jobs, preventing re-entrant Jolt work on a thread already inside a Jolt job, or giving Jolt back its own pool and accepting the oversubscription the adapter exists to avoid. `docs/architecture/extension-model.md` already names determinism as something a physics ABI must pin; this is the same argument arriving from the runtime side. FOUND BY the determinism gate as a side effect — it is unrelated to determinism, predates this work, and surfaced only because that test is the first thing in the tree to build and tear down two dozen runtimes with physics in one process. It is also why `determinism_gate_gating` is held out of the `unit` lane: the determinism it measures is ready to gate, this is not.
