## BUG-0055 — Jolt jobs on a general work-stealing pool: a use-after-free and a re-entrancy assert
- found:     2026-09-08
- status:    fixed
- class:     threading
- where:     src/plugins/jolt_jobs_adapter.h
- symptom:   a headless process running physics traps under CPU contention — `determinism_gate_test` under `ctest -j4`, roughly one run in ten. It needs load; 48 consecutive standalone runs are clean. Both traps land on the MAIN thread inside `JoltPlugin::onSimulationStop` or inside a Jolt job the main thread is executing, and in a Debug build they surface as Jolt's own asserts. With asserts compiled out the first is a silent use-after-free.
- cause:     `JoltJobsAdapter::QueueJob` hands a raw `Job*` to `jobs::run`, and Jolt's job system is designed around a pool it owns. Two distinct consequences, separated by lldb backtraces. **(a)** Nothing waited for queued jobs, so destroying the adapter freed the `FixedSizeFreeList` pages a still-queued lambda was about to run `job->Execute(); job->Release();` against — `JPH_ASSERT(mNumFreeObjects == mNumPages * mPageSize)` in `~FixedSizeFreeList`, from `onSimulationStop`. **(b)** `jobs::run` IS NOT ALWAYS ASYNCHRONOUS: enkiTS's `SplitAndAddTask` executes a task INLINE on the submitting thread when that thread's pipe is full (`TaskScheduler.cpp`, the `WriterTryWriteFront` failure path). Jolt spawns collision jobs from *inside* a collision job — `TrySpawnJobFindCollisions`, called from `JobFindCollisions` — so under contention a Jolt job began on a thread already running one. `JPH::BodyAccess` keeps read/write permission in THREAD-LOCAL state and asserts the thread is in the default state when a `Grant` is constructed, so the nested job tripped `JPH_ASSERT(velocity == EAccess::ReadWrite)`. The full 27-frame stack shows the whole chain in one call: `JobFindCollisions` -> `TrySpawnJobFindCollisions` -> `CreateJob` -> `QueueJob` -> `jobs::run` -> `AddTaskSetToPipe` -> `SplitAndAddTask` -> `ExecuteRange` -> the second `JobFindCollisions`.
- pinned-by: tests/determinism_gate_test.cpp
- lane:      determinism
- note:      THREE CHANGES, and (b)'s shape is the interesting one. (a): the adapter counts outstanding queued jobs and its destructor waits for zero, with a deadline that aborts loudly rather than corrupting. (b): `CreateJob` now WRAPS the job function in a thread-local depth scope, and `QueueJob` defers instead of submitting when that depth is non-zero. Wrapping the FUNCTION rather than our own pool lambda is what makes this complete — `Barrier::Wait` calls `Job::Execute()` directly on the waiting thread, so a wrapper around only our lambda would have missed that entry point entirely. Deferring is safe because `PhysicsSystem` adds every job to the step barrier immediately after `CreateJob` returns and `Barrier::Wait` executes any job it tracks — Jolt's own comment at that call site is "so the main updating thread can execute the job too" — and `Job::Execute` is CAS-guarded, so a job reached by both a worker and the barrier is fine. Third change: the destructor also RELEASES anything still deferred without running it, because a deferred job holds a reference and a `Job` whose refcount never reaches zero is never returned to the free list — that omission reintroduced (a)'s assert and is why the first attempt only halved the failure rate. Measured: from three SIGTRAPs in eight runs to zero in forty, under four competing physics processes. **What this does NOT fix, and it is a different bug:** underneath these, enkiTS's own `ICompletable` destructor asserts `GetIsComplete()` roughly once in fourteen runs at that same artificial contention — a `jobs::run` control block destroyed before its task finished. That is in the jobs facade, not the adapter, and it is recorded separately as BUG-0056.
