## BUG-0047 — the residency sweep paid for a full ECS scan it then threw away
- found:     2026-08-30
- status:    fixed
- class:     perf
- where:     src/runtime/runtime_frame.cpp
- symptom:   once a second, on the main thread, inside the frame: one heap allocation and a full walk of every entity in every world — **0.463 ms at 50 000 entities, measured** — whose result was discarded on the first line of the function it was built for.
- cause:     `frameBegin` built the `inUse` set BEFORE calling `evictOverBudget`, and that function opens with `if (!m_async || m_residencyBudget == 0) return 0;` followed by `if (total <= m_residencyBudget) return 0;`. The default budget is **0 = unbounded** — `runtime_boot.cpp:167` sets one only `if (cfg.meshBudgetMB > 0)` — so in the editor, and in any project that does not configure a mesh budget, the scan was pure waste every single time. Even with a budget set it was waste whenever the cache was under it, which is the normal state. The expensive part belonged to the caller, so only the caller could skip it: a function cannot decline an argument it has already been handed.
- pinned-by: tests/residency_test.cpp
- lane:      unit
- proof:     mutation, BOTH directions, because a wrong guard is worse than none. Forcing `residencySweepNeeded()` to return true fails "no budget -> no sweep" and "under budget -> no sweep" (the waste returns); forcing it false fails "OVER budget -> sweep" (the cache grows unbounded, which is the defect residency exists to fix). The test also asserts the guard AGREES with what it guards — when it says sweep, `evictOverBudget` must actually evict.
- note:      measured with a standalone flecs benchmark reproducing the exact scan shape: 0.092 ms at 5 000 entities, 0.236 at 20 000, **0.463 at 50 000**, 0.835 at 100 000. Against an 8.33 ms frame that is 5.5% at 50 k — not a catastrophe in the average, but it is a periodic SPIKE, and a spike once a second is what a player feels while an equivalent smear across sixty frames is not.
- note:      a second defect was introduced and caught while fixing this one. Folding the guard into the existing condition as `++m_residencyTick >= 60 && residencySweepNeeded()` short-circuits past `m_residencyTick = 0`, pinning the counter at 60 and running the guard on EVERY frame instead of every sixtieth — a cheaper check, sixty times more often. The reset has to happen whether or not a sweep follows.
- note:      the fix is a precondition, not the incremental used-set that was first proposed. Maintaining the set through flecs observers on `MeshRenderer`/`LodMesh` would make the sweep O(overage) instead of O(entities) — worth doing IF a configured budget ever makes the sweep hot — but it is a larger change and it would not have addressed the actual finding, which is that the work was being done when no work was needed at all.
