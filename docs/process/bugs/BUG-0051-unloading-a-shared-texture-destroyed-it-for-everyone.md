## BUG-0051 — unloading a shared texture destroyed it for everyone
- found:     2026-09-05
- status:    fixed
- class:     memory
- where:     src/runtime/services/asset_service.cpp
- symptom:   a material drawing the wrong texture, or a plausible-looking one, after any caller unloaded a texture another material shared. No crash and no log — TextureRegistry hands the freed slot to the next addTexture, so the second holder reads a live Texture that is simply the wrong one.
- cause:     `unloadTexture` was `return m_textures.removeTexture(h);` — a direct registry removal for a resource `m_texCache` dedups by path and REFCOUNTS. Two materials naming the same .ctex share one handle, and the first unload destroyed it regardless of the count. Three failures at once: the surviving holder pointed at a freed slot; TextureRegistry recycles slots off a free list with no generation counter, so that slot soon belonged to an unrelated texture; and both `m_texCache` and the async `loadedTextures` path->handle map kept naming the dead handle, so a later load or `queryTexture()` handed it out again. Reachable from Lua as `assets.unloadTexture`. `unloadMesh` and `unloadMaterial` immediately above it both invalidate their caches carefully — this was the one unload that never got it.
- pinned-by: tests/texture_ownership_test.cpp
- lane:      unit
- proof:     unloadTexture is now key-based for cache-owned textures — `m_texCache.keyFor(h)` then `release(key)`, letting the cache's destroyer do the eventual registry removal — and direct-with-invalidation for the async/importer population the cache does not own. The destroyer drops the async map entry in the same operation, so no path can free the slot and leave a map naming it. The test authors a real .ctex and drives the real load path: two acquisitions, one release still resident, zero references still resident (evictable is not dead), reload as a cache hit, over-release refused rather than underflowed, and a non-cached texture removed directly. Mutation: restoring the one-liner fails nine assertions and prints the refcount climbing 3, 4, 5, 6 against a destroyed texture.
- note:      a BEHAVIOUR CHANGE worth stating: nothing calls `evictOverBudget()` on the texture cache and no budget is set, so a cache-owned texture is now retained after its last release rather than freed immediately. That is the ctor's existing "eviction needs the reference counts to be complete first" gap, and retaining is the correct side to err on — exceeding a budget is recoverable, drawing from a freed slot is not. Wiring texture eviction is the follow-up this unblocks: the refcounts are now correct, which was the stated precondition.
