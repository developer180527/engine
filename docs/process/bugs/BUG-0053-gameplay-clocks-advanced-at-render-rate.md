## BUG-0053 — gameplay clocks advanced at render rate
- found:     2026-09-08
- status:    fixed
- class:     logic
- where:     src/runtime/runtime_sim.cpp
- symptom:   the same content, from the same starting state, produced DIFFERENT world state depending on the frame rate. A scene simulated at one frame per tick and at two frames per tick diverged on the very first tick — `Transform` for anything with a `Spinner`, `Animator::time` for anything animated. No crash, no log; the simulation simply was not a function of its inputs, so nothing about it could be regression-tested.
- cause:     `tickSystems()` runs once per FRAME with the frame's `dt`, and both the spinner query and `m_animatorSystem.tick(dt)` lived there — writing components the simulation owns. `tickSimulation()`'s fixed step advanced physics and scripts at `kSimDt` right next to them, so the engine had two clocks running gameplay at two rates. The animator's Snapshot-mode call (`m_animatorSystem.tick(*m_gameWorld, dt)`) and `m_gameWorld->progress(dt)` had the same problem, and `m_ecs.progress()` was called with NO `delta_time` at all — which flecs documents as "automatically measure the time passed since the last frame", i.e. a wall clock reaching the ECS pipeline.
- pinned-by: tests/determinism_gate_test.cpp
- lane:      unit
- proof:     Both clocks moved into the fixed step at `kSimDt`. `AnimatorSystem` is split along the line that decides it: `advance()` moves `Animator::time`, `Animator::playing` and the crossfade clocks (simulation state, hashed); `sample()` runs ozz and writes the bone palette (presentation, hashed by nothing); `tick()` remains both, for the editor viewport, where there is no fixed step to hang a clock on. `Spinner` moved to `stepSpinners()` — one body called from two places at two rates. `progress()` takes an explicit `dt` and the sim world's call moved into the step. The gate's `--gating` lane now runs the `static`, `spinner` and `scripting` tiers on both comparisons and fails on any divergence; mutation: restoring either frame-rate call turns two of those pairs red with an UNEXPECTED divergence and exit 1.
- note:      FOUND BY THE INSTRUMENT, ON ITS FIRST RUN, and not where it was predicted. The plan for the determinism gate hypothesised the animator would be the first render-rate coupling it caught; the gate reported `Spinner` first — the same defect one layer lower, in the engine's ONE demo gameplay system. That is the better finding, because it is in gameplay code rather than a subsystem, and it is the shape every gameplay system added from here has to avoid: **a component the simulation owns advances at `kSimDt` inside the fixed step; anything derived from it for display runs on the frame.** Splitting rather than simply relocating has a second payoff — the accumulator can run four fixed steps in one frame, and the old shape would have sampled four poses to show one. What the gate still reports is physics: contacts arrive from Jolt worker threads in thread-race order and land in `CollisionEvents`, which is a separate cause with its own fix.
