> **Research, 2026-11-26.** How other engines make subsystems swappable. The rules drawn from it are in [`provider-selection.md`](provider-selection.md) (DR-0037). Sources are linked inline; CryEngine was read from a 2018 public mirror.

# Engines decide providers early and fail late

Every major engine studied makes subsystems swappable the same basic way. Each implementation is a module that registers under a name. A project setting names the one to use, and a build switch decides whether modules are loaded as DLLs (development) or linked statically into one executable (shipping). They differ mainly in **when a bad choice is caught**. Unreal, Godot, O3DE and CryEngine all find a missing or unsupported provider at runtime: by falling back to a dummy, by ignoring the request with a warning, or by a fatal error at startup. O3DE and CryEngine go further and quietly stub out or disable unsupported backends at configure time, so the build passes. Only sokol_gfx refuses at compile time, with an `#error`. The per-frame cost of indirection is rarely a real problem, because the successful designs cross the provider boundary coarsely (one frame, one world step, one command list) rather than per object. The design we have planned (selection in project.json per platform, platform needs declared in CMake, `engine_build --platform` refusing an impossible choice by name, only GPU capability checks at startup) is stricter than any public engine on the point where they hurt most. It is a sound direction. The main risks it does not address by itself are behaviour drift between providers and content diverging between the "aaa" and "web" renderers.

## At a glance: how each engine swaps, selects and strips

| Engine / library | Unit of swap | Where the choice is made | How platforms are declared | How shipping strips | An unknown or unsupported choice gives |
|---|---|---|---|---|---|
| **Unreal Engine 5** | Module (DLL or static lib) in a plugin | Ini (`DefaultGraphicsRHI`, `AudioMixerModuleName`), command line overrides at startup | `.uplugin` `SupportedTargetPlatforms`, module `PlatformAllowList`/`DenyList`, Platform Extensions folders | Monolithic link of enabled plugins; Developer/Editor modules never ship | Runtime failure (a bad audio ini breaks init) |
| **Unity 6** | Settings asset or package; native engine is monolithic | Editor settings: render pipeline asset per quality level, ordered graphics API list per platform | `.asmdef` include/exclude platform lists, plugin import settings | IL2CPP managed and engine code stripping; Physics SDK "None" strips PhysX | Next API in the list; Editor falls back to a built-in list |
| **Godot 4** | "Server" registered with a manager | Project setting string with `.windows`/`.web` style overrides, read at startup | SCons `can_build(env, platform)` per module | Module flags, `disable_*` options, build profiles | Default server, then a Dummy, with a warning |
| **O3DE** | Gem (CMake target + gem.json) | `--rhi`, then a settings-registry priority list, then factory defaults | Per-gem PAL CMake traits | `LY_MONOLITHIC_GAME` makes every gem static | Empty alias or stub compiles; failure appears at runtime |
| **CryEngine 5** | Engine module behind an interface | Cvars (`r_Driver`, `p_physics_library`, `s_AudioImplName`) | CMake options per renderer/audio backend; `.cryproject` plugin `platforms` | `OPTION_STATIC_LINKING`, static factory registry | SDK missing: silently disabled. Runtime: `CryFatalError` |
| **Bevy** | Plugin (crate) | Code (`DefaultPlugins` builder) plus Cargo features | `#[cfg]` on target and features | Disabled features are never compiled | Panic if a referenced plugin is absent |
| **Source 2** | Render-system DLL | `-vulkan` launch option | Not public | Not public | Not public |
| **bgfx** | Backend inside the library | `bgfx::init` renderer type | `BGFX_CONFIG_RENDERER_*` with per-platform defaults | Undefined backends are not compiled | Tries the next supported backend |
| **sokol_gfx** | One backend per build | Preprocessor define | The define itself | Only one backend exists | `#error` at compile time |
| **SDL3 GPU** | Backend inside the library | `SDL_HINT_GPU_DRIVER` at runtime | `#ifdef SDL_GPU_*` | Undefined backends are not compiled | Error "unsupported" |
| **NVRHI / Diligent** | Backend inside the library | Application creates the device | CMake options (`NVRHI_WITH_*`, `DILIGENT_NO_*`) gated by platform | Options off means not built | Application's responsibility |

## Modules registered by name are the universal mechanism

The unit of swap is almost always a **module that registers itself under a name, looked up through a registry**. In Unreal, a module implements `IModuleInterface` and registers with `IMPLEMENT_MODULE`. Plugins group modules and carry per-platform, per-target and per-configuration allow and deny lists ([Epic: Modules](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules); [SchemaStore uplugin.json](https://www.schemastore.org/uplugin.json)). Implementations are found by a module name read from ini, or through the `IModularFeatures` registry, which plugins use "to augment or replace existing modular features" ([Epic API: IModularFeatures](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/IModularFeatures)). Godot is the cleanest example. Each subsystem has a manager with `register_server(name, factory)` and `set_default_server(name, priority)`. The editor dropdown for `physics/3d/physics_engine` is built from whatever registered, and the setting is marked restart-on-change ([physics_server_3d_manager.cpp](https://github.com/godotengine/godot/blob/master/servers/physics_3d/physics_server_3d_manager.cpp)). O3DE uses `AZ::Interface<T>` singletons. An RHI backend registers a `Factory`, and `Factory::Get()` asserts when none is connected ([Factory.cpp](https://github.com/o3de/o3de/blob/development/Gems/Atom/RHI/Code/Source/RHI/Factory.cpp)).

**CryEngine shows the most useful pattern for us.** `InitializeEngineModule` first asks a static factory registry for the requested interface. Only if nothing is registered does it load a DLL by name and look again ([SystemInit.cpp, mirror](https://github.com/dymek91/CRYENGINE/blob/dymek/Code/CryEngine/CrySystem/SystemInit.cpp)). So the same by-name lookup works in development, where modules are DLLs, and in monolithic builds, where the factory is already linked in. O3DE does the equivalent in CMake: gem targets are declared with `PAL_TRAIT_MONOLITHIC_DRIVEN_MODULE_TYPE`, which becomes `GEM_MODULE` or `GEM_STATIC` depending on one switch ([Monolithic.cmake](https://github.com/o3de/o3de/blob/development/cmake/Monolithic.cmake)). Two plugin-era engines chose a pure C boundary for ABI stability. Our Machinery published APIs as structs of C function pointers in a registry, because C++ requires a matching compiler, version and flags, and its plugins could be "link[ed] statically or dynamically" ([Our Machinery, part 1](https://ruby0x1.github.io/machinery_blog_archive/post/little-machines-working-together-part-1/); [part 2](https://ruby0x1.github.io/machinery_blog_archive/post/little-machines-working-together-part-2/)). Bitsquid and Stingray served versioned C tables by ID, `get_plugin_api(api_id)`, "to avoid ABI incompatibilities" ([Bitsquid blog](https://bitsquid.blogspot.com/2014/04/building-engine-plugin-system.html); [Stingray plugin_api.h](https://help.autodesk.com/cloudhelp/2018/ENU/Max-Interactive-Help/engine_c/plugin__api_8h.html)).

Two engines sit outside this pattern. Unity selects through **data assets in the editor**. The render pipeline is a `RenderPipelineAsset` resolved per quality level, falling back to the Graphics default and then the built-in pipeline ([Unity: Set the active render pipeline](https://docs.unity.com/en-us/engine/6000.0/manual/render-pipelines/choose-a-render-pipeline/srp-setting-render-pipeline-asset)). Its native engine stays monolithic. Bevy selects through **code and Cargo features**: every entry in `DefaultPlugins` is `#[cfg(feature = ...)]`-gated, and a replacement such as bevy_kira_audio requires turning off the built-in `audio` feature ([default_plugins.rs](https://github.com/bevyengine/bevy/blob/main/crates/bevy_internal/src/default_plugins.rs); [bevy_kira_audio README](https://github.com/NiklasEi/bevy_kira_audio/blob/main/README.md)).

Physics is where swapping is weakest. Unreal's PhysX-to-Chaos switch was a compile-time interface choice, and Epic has said "over time some of the abstraction code will be removed" ([Epic forum](https://forums.unrealengine.com/t/how-to-enable-physx-in-ue5/519946/2)). Godot is the counter-example: Jolt and GodotPhysics sit behind one `PhysicsServer3D`, and Jolt became the default for new projects in 4.6 ([Godot 4.6](https://godotengine.org/releases/4.6/)).

## The choice is made once at startup, and coarse boundaries hide its cost

No engine studied swaps a renderer mid-process. Unreal reads `DefaultGraphicsRHI` during `LoadDynamicRHIModule`, and `-d3d12`/`-vulkan` override it at startup, but any change needs a restart ([indxzero UE 5.4 wiki](https://indxzero.github.io/ue544cvarwiki/articles/defaultgraphicsrhi); [Epic forum](https://forums.unrealengine.com/t/rhi-switching-dx11-dx12-vulkan-during-runtime/571030)). Godot marks its physics setting restart-on-change. Source 2 picks its Vulkan render system with a launch option ([Valve wiki](https://developer.valvesoftware.com/wiki/Vulkan)). The one runtime hot swap found is CryEngine's audio: changing the `s_AudioImplName` cvar unloads the current middleware implementation and loads the new one ([CryAudioSystem.cpp, mirror](https://github.com/dymek91/CRYENGINE/blob/dymek/Code/CryEngine/CryAudioSystem/CryAudioSystem.cpp)). Unity can also switch render pipelines live in the editor, but assets that do not match the pipeline break ([Unity](https://docs.unity.com/en-us/engine/6000.0/manual/render-pipelines/choose-a-render-pipeline/srp-setting-render-pipeline-asset)).

**Per-frame cost is handled by crossing the boundary rarely, not by removing the virtual call.** Unreal's render thread records small `FRHICommand` structs, and a separate RHI thread translates them against the chosen backend ([Epic: Threading overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/parallel-rendering-overview-for-unreal-engine)). bgfx hands the whole recorded frame to the backend in a single virtual `submit(Frame*)` ([bgfx_p.h](https://github.com/bkaradzic/bgfx/blob/master/src/bgfx_p.h)). Unity's C# pipeline submits culling results and draw lists, never single objects, and the SRP Batcher keeps material constant buffers resident on the GPU so unchanged materials cost no state changes ([Unity: SRP Batcher](https://docs.unity3d.com/2023.2/Documentation/Manual/SRPBatcher.html)). Godot's servers are plain C++ virtual interfaces. A `WrapMT` decorator queues calls from other threads, so a provider never has to be thread-aware ([physics_server_3d_wrap_mt.h](https://github.com/godotengine/godot/blob/master/servers/physics_3d/physics_server_3d_wrap_mt.h)).

The measured cost of a virtual call is mostly **lost inlining**, not the branch. Bendersky found about a 6x gap between virtual and CRTP dispatch in a tight loop, and the gap reversed when inlining was disabled ([Bendersky, 2013](https://eli.thegreenplace.net/2013/12/05/the-cost-of-dynamic-virtual-calls-vs-static-crtp-dispatch-in-c/)). That cost matters only for fine-grained calls. Libraries that want zero indirection pick one backend per build: sokol_gfx dispatches through `#if` chains with no runtime table at all ([sokol_gfx.h](https://github.com/floooh/sokol/blob/master/sokol_gfx.h)). Clang's `-fwhole-program-vtables` with LTO can devirtualise a C++ interface that has only one linked implementation, but only with hidden visibility and no dlopened subclasses ([llvm-dev RFC](https://groups.google.com/g/llvm-dev/c/6LfIiAo9g68)). It does not apply to tables of C function pointers. No public engine benchmark of per-draw dispatch cost was found.

## Platforms are declared in build metadata, but enforcement is uneven

Each engine has a declaration point. Unreal uses `.uplugin` platform lists and **Platform Extensions**: since 4.23, all code for a platform lives under `Engine/Platforms/<Platform>/` and is simply absent unless installed. To allow that, `UnrealTargetPlatform` was changed from an enum to an extensible class ([Epic forum: Platform Changes Ahead](https://forums.unrealengine.com/t/attention-platform-changes-ahead/126005)). Unity's `.asmdef` files take an include list *or* an exclude list, never both ([Unity: asmdef format](https://docs.unity.com/en-us/engine/6000.0/manual/programming-environment/script-compilation/assembly-definition-files/file-format)). Godot modules answer `can_build(env, platform)`, and its platform scripts switch backends off when a dependency is missing ("wayland-scanner not found. Disabling Wayland support.") ([SConstruct](https://github.com/godotengine/godot/blob/master/SConstruct); [detect.py](https://github.com/godotengine/godot/blob/master/platform/linuxbsd/detect.py)). O3DE uses per-gem PAL files: on Linux, for example, the DX12 gem's PAL file sets `PAL_TRAIT_ATOM_RHI_DX12_SUPPORTED FALSE` ([PAL_linux.cmake](https://github.com/o3de/o3de/blob/development/Gems/Atom/RHI/DX12/Code/Source/Platform/Linux/PAL_linux.cmake)). Console code lives outside the main tree under a placeholder name ([Gems.cmake](https://github.com/o3de/o3de/blob/development/cmake/Gems.cmake)). CryEngine has CMake options per backend (`RENDERER_VULKAN`, `AUDIO_WWISE`, and so on), and `.cryproject` plugins carry a `platforms` filter ([BuildEngine.cmake, mirror](https://github.com/dymek91/CRYENGINE/blob/dymek/Tools/CMake/BuildEngine.cmake); [CryPluginManager.cpp, mirror](https://github.com/dymek91/CRYENGINE/blob/dymek/Code/CryEngine/CrySystem/ExtensionSystem/CryPluginManager.cpp)). Rendering libraries do the same with CMake options gated by platform, for example `NVRHI_WITH_DX12` being Windows-only ([NVRHI CMakeLists](https://github.com/NVIDIA-RTX/NVRHI/blob/main/CMakeLists.txt); [DiligentCore CMakeLists](https://github.com/DiligentGraphics/DiligentCore/blob/master/CMakeLists.txt)).

The common weakness is that **unsupported means "quietly absent", not "refused"**. O3DE's Vulkan gem creates an empty alias target and returns when the platform trait is false, and PhysX5 compiles "unsupported" stub files. The build passes, and the failure appears as a runtime assert ([Vulkan CMakeLists](https://github.com/o3de/o3de/blob/development/Gems/Atom/RHI/Vulkan/Code/CMakeLists.txt); [PhysX5 CMakeLists](https://github.com/o3de/o3de/blob/development/Gems/PhysX/Core/PhysX5/CMakeLists.txt)). The `platforms` field in gem.json does not appear to be read by the CMake build at all ([gem_properties.py](https://github.com/o3de/o3de/blob/development/scripts/o3de/o3de/gem_properties.py)). CryEngine disables an audio backend when its SDK is missing and records the reason only in a CMake cache tooltip. Unreal users report that non-targeted platforms are compiled anyway, and that a missing `PlatformAllowList` entry gives "bizarre errors in logs" ([Epic forum](https://forums.unrealengine.com/t/non-targeted-platforms-in-uplugin-file-building-anyway-when-packaging-a-c-plugin/2022383); [Epic forum](https://forums.unrealengine.com/t/platformallowlist-missing-runtime-platform-gives-bizarre-errors-in-logs/1504254)). Unity's plugin inspector states plainly that "Unity does not validate your settings" for Android CPU ([Unity: Plug-in Inspector](https://docs.unity.com/en-us/engine/6000.0/manual/programming-environment/plug-ins/plug-in-inspector)).

## Shipping builds strip by linking only what was enabled

Shipping stripping is the same idea everywhere: **one switch turns the whole module graph into static libraries, and only enabled modules are linked.** Unreal's `LinkType` picks monolithic or modular linking. Developer modules are "never in shipping builds", and per-platform plugin enablement sits in the .uproject ([UBT Target reference](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-build-tool-target-reference); [Epic: Plugins](https://dev.epicgames.com/documentation/en-us/unreal-engine/plugins-in-unreal-engine)). O3DE's `LY_MONOLITHIC_GAME` makes every gem static, and the same switch also turns off tools, tests and benchmarks ([Monolithic.cmake](https://github.com/o3de/o3de/blob/development/cmake/Monolithic.cmake)). CryEngine forces `OPTION_STATIC_LINKING` on for PlayStation and Android ([CommonOptions.cmake, mirror](https://github.com/dymek91/CRYENGINE/blob/dymek/Tools/CMake/CommonOptions.cmake)). Godot removes a physics backend with `module_godot_physics_3d_enabled=no`, and `disable_3d` alone shrinks a build by "about 15%" ([Godot: Optimizing for size](https://docs.godotengine.org/en/latest/engine_details/development/compiling/optimizing_for_size.html)). Unity is the late-binding exception. Setting Physics to "None" together with "Strip Engine Code" removes the built-in physics integrations from the player ([Unity: Remove the physics backend](https://docs.unity3d.com/6000.4/Documentation/Manual/physics-remove-backend.html)). Its managed stripping is static analysis that cannot see reflection, so code has to be preserved by hand ([Unity: Managed code stripping](https://docs.unity.com/en-us/engine/6000.0/manual/programming-environment/script-compilation/managed-code-stripping)).

Two precedents shape how this works for us. First, Bevy's Cargo features are additive across the dependency graph, so any dependency can quietly re-enable a built-in that the project meant to replace. A check by name catches that kind of mistake. Second, O3DE's monolithic mode disables tests, so **the shipped configuration is not the one the test suite exercises** unless CI builds and smoke-tests it separately.

## Decoupling relies on neutral buffers, opaque handles and capability data

Providers that must cooperate meet in **engine-owned neutral formats**, never in each other's types. For physics debug drawing, Unreal's Chaos writes to a thread-local debug-draw buffer (`FChaosDDContext`) that an engine-side component draws ([Epic API: FChaosDDContext](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Chaos/FChaosDDContext)). O3DE gems emit to a framework-level `DebugDisplayRequestBus` without depending on Atom ([EntityDebugDisplayBus.h](https://github.com/o3de/o3de/blob/development/Code/Framework/AzFramework/AzFramework/Entity/EntityDebugDisplayBus.h)). Godot never asks the physics server to draw at all: scene nodes build debug meshes from shape data they already own and submit them to the RenderingServer ([collision_object_3d.cpp](https://github.com/godotengine/godot/blob/master/scene/3d/physics/collision_object_3d.cpp)). Windows cross the boundary as an opaque handle. Unreal's `RHICreateViewport` takes the `void*` from `FGenericWindow::GetOSWindowHandle()` ([UE 4.26 API](https://docs.unrealengine.com/4.26/API/Runtime/RHI/RHICreateViewport/index.html)), and in Godot the DisplayServer owns the windows and creates the rendering-context surfaces ([rendering_device_driver.h](https://github.com/godotengine/godot/blob/master/servers/rendering/rendering_device_driver.h)). Middleware audio sits behind a translation layer, the ATL, in both CryEngine and O3DE ([O3DE AudioSystem](https://github.com/o3de/o3de/tree/development/Gems/AudioSystem/Code/Include)).

Capabilities are exposed as **data, not type queries**. Unreal uses feature levels, data-driven shader platforms and `FRHIGlobals` flags, and Nanite requires DX12 with SM6 ([Epic: ERHIFeatureLevel](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/RHI/ERHIFeatureLevel__Type); [Epic: features by rendering path](https://dev.epicgames.com/documentation/en-us/unreal-engine/supported-features-by-rendering-path-for-desktop-with-unreal-engine)). Fallback is an ordered list. Unity tries the next graphics API in the list when one is unsupported ([Unity: Configure graphics APIs](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/cross-platform-features/graphics-apis/configure)). Godot has `fallback_to_vulkan`, `fallback_to_d3d12` and `fallback_to_opengl3` flags, and its X11 display server drops to GL Compatibility when Vulkan fails ([main.cpp](https://github.com/godotengine/godot/blob/master/main/main.cpp)). bgfx marks a backend unsupported when creating it fails and tries the next one ([bgfx.cpp](https://github.com/bkaradzic/bgfx/blob/master/src/bgfx.cpp)). CryEngine checks the GPU feature level before it loads the D3D renderer, and shows "Unsupported GPU configuration!" below DX11 ([SystemInit.cpp, mirror](https://github.com/dymek91/CRYENGINE/blob/dymek/Code/CryEngine/CrySystem/SystemInit.cpp)). Automatic fallback is not reliable everywhere: Unreal users report the default Windows RHI choosing DX12 on hardware that cannot run it ([Epic forum](https://forums.unrealengine.com/t/windows-default-rhi-selection-chooses-dx12-on-older-incompatible-devices/2745476)).

The main coupling to avoid is global state. CryEngine passes an environment into each module's `Initialize`, but it *also* exposes the same environment as the global `gEnv`, and it had to remove `gEnv->pGame` to cut engine-to-game coupling ([CRYENGINE 5.3 changes](https://www.cryengine.com/docs/static/engines/cryengine-5/categories/47316993/pages/44962674)).

## Pain points: behaviour drift, late failure and fragmented content

The documented pain falls into four groups. **Same interface, different behaviour.** Users moving from PhysX to Chaos reported steps of about 100 ms against about 5 ms, bodies tunnelling and broken constraints, and Epic's migration guide says Chaos "behaves differently from PhysX, requiring developers to make adjustments" ([Epic forum](https://forums.unrealengine.com/t/chaos-physics-in-ue5-ea-and-beyond/231748); [UE5 migration guide](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-5-migration-guide)). Godot documents a long list of Jolt divergences behind one API, covering margins, Baumgarte stabilisation, joint soft limits and ray `face_index` ([Godot: Using Jolt Physics](https://docs.godotengine.org/en/latest/tutorials/physics/using_jolt_physics.html)). **Late failure.** An empty `AudioMixerModuleName` breaks Unreal's audio at runtime ([Epic forum](https://forums.unrealengine.com/t/audio-device-manager-not-working/1697097)). O3DE ignores a `--rhi` naming an unregistered backend with only a warning ([FactoryManagerSystemComponent.cpp](https://github.com/o3de/o3de/blob/development/Gems/Atom/RHI/Code/Source/RHI.Private/FactoryManagerSystemComponent.cpp)). Wwise's Debug/Profile/Release library matrix shows up as LNK1181 and LNK2038 errors at link time ([Audiokinetic Q&A](https://www.audiokinetic.com/qa/12351/ild-fatal-error-lnk1181-cannot-input-communicationcentral)). **Fragmented content.** Unity is deprecating its Built-in pipeline and has frozen HDRP features, citing "the complexity that comes from fragmented options", because shaders and assets were tied to one pipeline ([Unity: Render pipelines strategy 2026](https://unity.com/topics/render-pipelines-strategy-for-2026)). **Hidden configuration and implicit order.** Unreal's `-d3d12` switches write a per-user `Saved` ini ([Epic forum](https://forums.unrealengine.com/t/how-to-set-defaultgraphicsrhi/569747)). Bevy contributors describe dependencies between plugins as "implicit even when reading the code" ([bevy#18187](https://github.com/bevyengine/bevy/pull/18187)). Hot reload is costly too: Our Machinery had to keep both DLL versions loaded and work around Windows file locks.

Studios that want no abstraction cost simply reduce the number of backends. id Tech 7 is Vulkan-only on PC ([Wikipedia: id Tech 7](https://en.wikipedia.org/wiki/Id_Tech_7)). Platform separation that is retrofitted is expensive: Epic called the 4.23 platform refactor "likely the largest change for developers".

## Recommendations for our engine

**Keep the three layers separate and give each its own failure point.** Provider choice (renderer, audio, physics) is resolved and validated by `engine_build --platform`. The graphics API backend inside librhi is chosen at startup from the backends compiled for that platform. Hardware capability is checked at startup against what the chosen renderer requires. Nothing else is decided at runtime, and nothing falls back silently. This is the one place where we deliberately go further than every engine above.

**Declare each provider once, in CMake, through a single macro.** Something like `engine_provider(NAME aaa SLOT renderer PLATFORMS windows linux macos ios android NEEDS rhi:any SDKS ...)`. The macro creates a MODULE target in dev builds and a STATIC target in shipping builds, as O3DE's `PAL_TRAIT_MONOLITHIC_DRIVEN_MODULE_TYPE` does. It also writes a machine-readable manifest that `engine_build` reads. Use an allow list of platforms only, never an exclude list, so a new platform starts with no providers instead of inheriting them. A missing SDK must be a hard error that names the provider and the SDK path, never CryEngine's silent auto-disable. Platform-specific providers and NDA platform code belong in drop-in directories from the start, which is the layout Unreal had to retrofit.

**Make project.json resolution simple and strict.** A per-platform key wins; otherwise `default` applies (`"renderer": {"default":"aaa","web":"web"}`), which mirrors Godot's `.web`/`.windows` suffixes. Before configuring, `engine_build --platform X` should check five things and refuse by name with a fix-it message: the slot exists; the provider exists; the provider lists X; its `NEEDS` are met on X (for example, a renderer requiring Vulkan or D3D12 cannot target web); and exactly one provider fills each slot (O3DE's `provided_unique_service` idea, enforced rather than advisory). Add a sixth check for middleware that ships per-configuration libraries (Wwise Debug/Profile/Release), so a missing library is refused before link time instead of failing with LNK1181. Keep project.json the only source of truth. A dev-only command-line override is fine, but it must never persist into per-user state.

**Register statically linked providers explicitly.** Copy CryEngine's single lookup: static registry first, `dlopen` second, the same C entry point either way. In shipping builds, have `engine_build` generate one small source file that calls each chosen provider's `register` function. Do not rely on static-initializer self-registration, because linkers can discard unreferenced objects from static libraries. A generated call list also documents exactly what the binary contains.

**Keep the C API coarse, and only then consider devirtualisation.** Provider entry points should take a frame, a view list, a world step or a batch of events, as bgfx's `submit(Frame*)` and Unity's draw lists do, never a per-object setter. At that granularity one indirect call through a C function table costs nothing measurable, so start with tables in both dev and ship. If profiling of the *shipping* build shows otherwise, add a sokol-style direct-call header for monolithic builds. Do not judge from dev-build profiles: calls across a DLL boundary can never be inlined, so dev builds overstate the cost.

**Treat librhi backends like bgfx and NVRHI do, but strict.** Gate D3D12, Vulkan and Metal per platform with CMake options, so Apple builds contain only Metal and need no runtime choice. On Windows and Linux, compile the allowed set and pick from an ordered list in project.json (Unity's model). Probe the device, and if no compiled backend meets the renderer's declared minimum, fail with a clear message, as CryEngine's feature-level check does. Expose capabilities as a plain data struct through the C API, so renderers branch on features, never on which API is running.

**Decouple providers through engine-owned formats.** Physics writes debug lines and shapes into an engine debug-draw buffer that whichever renderer is active consumes (the Chaos and O3DE pattern). The platform layer hands the renderer an opaque native window handle. Each provider's `init` receives a context struct; there is no global `gEnv`. Dependencies between providers go in the CMake `NEEDS` declaration, not in runtime discovery (the Bevy lesson).

**Write down behaviour contracts and test them.** For each slot, specify semantics in the C API documentation: collision margins, penetration recovery, trigger rules, the joint model and query result fields for physics; latency and voice-limit behaviour for audio. Then run one conformance suite against every provider. Give each provider its own settings namespace, as Jolt has in Godot. For the renderer, hold "aaa" and "web" to **one asset and material contract**, with a declared feature subset that the web renderer degrades to predictably. Unity's fragmentation is what happens without that.

**Test what ships.** Every slot needs an explicit Null provider (like O3DE's Null RHI and bgfx's Noop), which serves the headless test farm and dedicated servers. It is selected by name and is never a fallback. CI should build the monolithic shipping configuration for each platform and provider combination we support and run a smoke test, because O3DE's experience shows monolithic builds otherwise go untested. Changing a provider in dev should mean a restart, which is Godot's and Unreal's rule, not hot swapping; hot reload's costs on Windows are well documented and the benefit is small.

## Conclusion

The research changes the framing of the problem. Swappability itself is solved: every engine has a registry, a name and a static-or-dynamic switch, and the per-frame cost is negligible once the boundary is coarse. What separates designs is where errors surface, and the industry's habit of degrading gracefully (stubs, dummies, warnings, auto-disabled SDKs) turns configuration mistakes into runtime surprises on a device. Refusing by name at build time is cheap to build because the data already exists in CMake and project.json, and it removes the most common class of failure documented in this research.

The harder, open problem is semantic. Unreal and Godot both show that two providers behind one interface behave differently, and Unity shows that two renderers drift into two content ecosystems. Our build-time checks can prove that a choice is *possible*. Only behaviour contracts, conformance tests and one shared asset contract can make the choice *safe*, so those deserve as much design effort as the build plumbing.
