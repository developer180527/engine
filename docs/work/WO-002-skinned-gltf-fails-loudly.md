## Why
A skinned `.glb` silently loses its skeleton and animations and cooks as a static mesh.

`cookGltf` never reads `data->skins` or `data->animations`, and Assimp is built without glTF, so nothing falls back. This is the one finding in the review that is losing data today. The real fix is WO-014. This order makes the loss impossible to miss until then.

## Done when
- [x] `cookGltf` refuses a file whose `skins_count > 0` (or whose `animations_count > 0` with no meshes). The error names what would be lost: "N skins, M animations — skinned glTF is not supported yet (WO-014)".
- [x] the runtime `GltfImporter` warns once per file for the same condition
- [x] a small skinned glTF test fixture, generated by the test rather than checked in as a binary: its cook is refused with that message, and a static glTF still cooks
- [x] mutation: removing the check turns the test red
- [x] the stale comment at `mesh_cooker.cpp` ("Skinned meshes … cannot be cooked yet … Skip cooking"), which sits directly above the line that cooks them, is corrected

## Contract
Tightens `cooker`'s **Errors** section: a feature in the source that the cooked format cannot carry is a *refusal that names what was lost*, never a success.

Nothing: the cook result is `success=false` with a human-readable reason. The runtime importer logs once and keeps loading the static geometry, which is today's behaviour, but no longer silently.

## Not in scope
Actually supporting glTF skins (WO-014).

## Log
- 2026-09-30: `src/assets/importers/gltf_losses.h` is the one judgement both
  glTF paths use: skins → refuse; animations with no mesh → refuse, named
  (it used to fail as "no triangle geometry"); node animations on a static
  mesh → cook the mesh and report the dropped animations. That third case is
  a judgement call beyond the order: refusing it would break props that cook
  correctly today, and the mesh alone is still correct.
- The runtime `GltfImporter` warns once per file through the same function.
  The warn-once wrapper itself is not under test: the logger has no capture
  hook, and adding one is out of scope. The judgement it prints is tested.
- The fixture is generated by the test and passes `cgltf_validate`, so it is
  a real glTF, not something only our parser accepts.
