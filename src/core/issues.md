# technical gaps hidden across the core files:

•	Recursive Transform Bottleneck: Both getWorldMatrix and getWorldMatrixLerp lack a transform cache, meaning they recursively walk the flecs ChildOf parent chain up to a depth of 256 every single time an entity's matrix is evaluated. This triggers redundant parent matrix lookups and heavy bx::mtxMul calls across rendering and editor operations.
•	Un-reserved Debug Allocation Storms: The DebugDraw utility uses a raw std::vector without pre-allocating memory during geometric tessellation. Hot methods like circle and sphere push vertices directly via push_back, meaning a sudden frame spike in debug rendering will trigger massive, multi-step vector resizing and heap-copying operations on the fly.
•	The Synchronized Logger Trap: The Logger::log method performs a highly expensive O(N) linear shift (m_entries.erase(m_entries.begin())) on its backing std::vector every single time it passes the 1024-entry cap. Because this array modification happens directly inside a global std::lock_guard mutex, it can heavily serialize calling threads. Additionally, the hardcoded 1024-byte char buf stack layout will quietly truncate any long, serialized log messages or crash dumps.
•	FrameArena Overflows & Concurrency Limits: FrameArena is strictly single-threaded, leaving it highly vulnerable to race conditions if accessed by a worker thread without an individual instance. Furthermore, its overflow fallback drops down to slow, platform-specific heap routing (_aligned_malloc or posix_memalign) tracked inside a dynamic std::vector, completely stripping away its O(1) time complexity guarantee when capacity is blown.
•	Memory Profiling Gaps: The global profiling counters suffer from a tracking blindspot where over-aligned forms of custom operators new and delete (used for unique SIMD/vector structures) entirely bypass the tracking atomics in the v1 implementation.
