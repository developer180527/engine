render: materials become data at the draw call

The .cmat half of Phase 5. A material authored as JSON, cooked against a
shader's declared interface, now reaches an actual draw call, and the engine
never learns what it looks like.

Verified live in fps_shooter, the whole chain in one run:

  [ForwardPipeline] standard program: cooked .cshader
  [AssetService] Loaded material: zombie_sickly -> shader "standard"
                 (2 block(s), 2 texture(s), features 0x0)
  [Game] zombie material asset -> handle 5
  [ForwardPipeline] data-driven bind: material 5 on shader "standard"

That last line exists because "the .cmat loaded" and "the .cmat is what you are
looking at" are different claims, and only the second one is the feature. It
logs once per material from inside the bind branch.

THE DESIGN PROBLEM WORTH RECORDING. u_params packed material values (roughness,
metallic) alongside ENGINE-DRIVEN flags (hasBaseColor, hasNormalMap) in one
vec4. A cooked material's uniform block covers its whole register, that is what
makes blocks complete rather than sparse, so binding one would have zeroed
those flags and every textured surface would have gone flat white. Split in
fs_triangle.sc: u_params is material-owned, u_texFlags is engine-driven and
derived from what is actually resident. The rule is general, not a patch: a
material owns whole registers, so nothing engine-driven may share one.

The runtime does NO name lookup and NO validation on the material path. The
cooker resolved every name, checked arity and filled defaults offline; repeating
any of it here would be a second source of truth free to drift from the first.
AssetService copies blocks verbatim and resolves textures through the existing
dedup/residency path, so a material sharing an image with a mesh uploads once.

.cmat gains the shader's declared NAME (v1 -> v2). It stored only the authored
path, but the runtime resolves by name, a dist has no registry, and deriving
the name from a filename would have been a third convention to keep in sync.

Two small engine-API additions, which are the actual feature rather than test
scaffolding: engineAssetLoadMaterial(path) and engineEntitySetMaterial(entity,
handle). A game applies an authored look; the engine knows nothing about it.

A data-driven material picks its own program per draw, reset per submesh so it
cannot leak to the next range. If that program is missing (wrong backend,
uncooked variant) the draw falls through to the fixed path rather than
vanishing, and ShaderLibrary has already said why, once.

Verified: full build clean, ctest unit 30/30, engine_doctor 60 docs / 0 errors.
