build: extract + test sceneMeshRefs, a scene that won't load dropped silently

collectSceneMeshRefs decided which meshes ship at all, lived as a static in
engine_build.cpp, and had no test. Its failure mode was worse than the
untextured one already fixed: an unreadable cooked scene hit a bare `continue`,
so every object in it vanished from the package with no output whatsoever. One
version-bumped or half-written scene and the shipped game is empty.

Now pkg::sceneMeshRefs(), returning what shipped AND what didn't:

  meshes            deduplicated across scenes, a mesh in two scenes ships once
  unreadableScenes  named, so engine_build warns instead of continuing past
  scenesRead        zero, with a directory present, means a package with no content

Also made deterministic. directory_iterator order is filesystem-defined, so the
scene walk is sorted first: a package that differs run to run makes "did this
build change?" unanswerable, and that difference would only ever be noticed as a
mysterious diff in shipped bytes.

Tests cover: collection across scenes with dedup, an unreadable scene NAMED
while readable ones still contribute, meshless entities (lights, cameras, spawn
points, the common case) skipped rather than collected as empty strings,
non-.cooked files ignored, and an absent directory yielding nothing instead of
throwing.

MUTATION-PROVED, both ways: restoring the silent `continue` fails the
unreadable-scene assertion; removing the sort fails the ordering one.

On that ordering assertion, it writes its scenes in REVERSE alphabetical order
so that a filesystem returning creation order exposes an unsorted walk. On a
filesystem that returns sorted order it would pass either way. That is real
coverage on some hosts and vacuous on others, never a false failure, and it is
said so in the test: a test that cannot fail is worse than no test if you
believe it can. It does bite on APFS here, verified by removing the sort.

Verified: full build clean, ctest unit 30/30, engine_doctor 59 docs / 0 errors,
and a real engine_build of fps_shooter still produces an identical 53.7 MB dist
(3 scene mesh refs, 8 mesh files, 1 cooked shader).
