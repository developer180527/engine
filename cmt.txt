build: test the shader copy path, by NAME, not by file count

The last untested piece of packaging, and the one whose failure is quietest: a
package can contain cooked shader files and still leave the game on compiled-in
fallbacks, because the runtime resolves shaders by the NAME each .cshader
declares inside itself. The game renders correctly. Nothing looks wrong. The
project's custom shading simply never runs.

So pkg::shaderFiles() reports names, not counts, and engine_build now checks the
name the pipeline actually asks for:

  WARNING: no cooked shader declares "standard", the player will fall back to
  compiled-in shaders and custom shading will not run

Also surfaced: an unreadable .cshader is NAMED rather than shipped as dead
weight providing nothing, and two files declaring one name are flagged (normally
a stale cook from an older cooker version, one silently shadows the other).
Both copies still ship in that case: dropping one would make the package depend
on which file the packager saw first, and ShaderLibrary already resolves the
ambiguity deterministically.

MUTATION-PROVED three ways: counting files instead of reading declared names
fails 2 assertions, ignoring duplicate names fails 1, removing the sort fails 1.

That last one took two attempts and is worth recording. The first ordering
assertion named an expected element, and passed with the sort removed, because
this filesystem returned those entries sorted anyway. It was a test that could
not fail. Replaced with std::is_sorted (the exact contract a caller depends on)
plus a fresh directory written in reverse alphabetical order, which is what
actually gives it teeth: a filesystem returning creation order now exposes a
missing sort. Still vacuous on one that returns sorted entries, and the test
says so.

Verified: full build clean, ctest unit 30/30 (45 assertions in this test),
engine_doctor 59 docs / 0 errors, and a real engine_build of fps_shooter reports
"1 file(s) providing 1 name(s)" and produces an identical 53.7 MB dist.
