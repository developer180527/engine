render: cooked shaders can become programs, ShaderLibrary + roadmap audit

ForwardPipeline #includes metal/fs_triangle.sc.bin.h and friends, so the only
shaders that can ever execute are the ones the engine binary was compiled with.
That is the concrete mechanism behind finding R3. ShaderLibrary is the piece
that removes it: cooked .cshader in, bgfx program out.

Split so the part with decisions in it is testable:

  shader_select.h/.cpp   which variant does this machine want?   GPU-FREE
  shader_library.h/.cpp  load it, make the program, cache it     all bgfx

Two failures this guards, both silent otherwise and with completely different
fixes, so they get different messages:

  A PACKAGE COOKED FOR THE WRONG BACKEND. macOS cannot emit D3D bytecode, so a
  Mac-cooked package on a D3D11 machine has no usable variant. The program never
  builds and a renderer with no program draws NOTHING, a black screen with no
  error. The failure names the profiles that WERE cooked.

  A FEATURE MASK NEVER COOKED. Selection is an exact match, never nearest.
  Falling back to a different feature set renders confidently wrong output: a
  skinned mesh drawn with the unskinned program collapses into a heap at the
  origin, which reads as an animation bug and costs a day.

Programs are content-keyed through GpuResourceCache like textures, keyed by
path # featureMask # profile, all three axes, because dropping any one means the
second material silently draws with the first's program. bgfx::copy not
makeRef: makeRef needs the bytes to outlive the frame and the parsed asset is
free to move.

Uniform handles are deduplicated here too. bgfx refcounts uniforms internally
but returns a NEW handle per createUniform call, so destroying one would destroy
a uniform another material still uses.

Tier is deliberately `prototype`, not `working`: the selection logic has real
coverage but NO running code path executes any of this yet.

Which is the point of docs/roadmap.md, added here. Three consecutive layers are
now built and unused, .cshader cooking, .material cooking, and this. That is
the moment to stop adding a fourth. The audit records what exists by tier, what
each renderer finding's real state is (verified against source, not memory: R4
is still live at forward_pipeline.h:272, R7 has no state comparison anywhere),
and names the single decision gating Phase 5, where the engine's own cooked
default assets live and how engine_build packages them, with a recommendation
rather than a guess.

Verified: full build clean, ctest unit 29/29 (was 28), engine_doctor 57 docs /
0 errors.
