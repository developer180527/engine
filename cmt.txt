assets: stage each .ctex once per mesh; measure reveals dev path uploads raw RGBA8

Worker staging: materials sharing an image (the pistol has 4 material
references to 2 files after the cooker's content dedup) each read the file and
bgfx::copy'd it again. The worker now stages a given .ctex once per mesh and
the drain resolves skipped materials to the first user's handle by name.

The skip MUST happen on the worker, not at the drain: bgfx memory from copy()
is freed only when a create call consumes it, so discarding an
already-allocated duplicate later would leak it. Not allocating is the only
safe form of "don't upload this twice". Scope is one mesh; cross-mesh sharing
needs the worker to consult the main-thread cache safely, which is next.

MEASUREMENT REFRAMES THE PROBLEM. VRAM did not move (76 MB), because
engine_host does not use this path at all:
  engine_host  (dev)     SceneSerializer -> ImporterRegistry -> glTF importer
  engine_player (shipped) SceneService   -> AssetService     -> cooked .ctex
gltf_importer's uploadRGBA creates TextureFormat::RGBA8 with mips=false, so one
4096x4096 texture costs 64 MB uncompressed and unmipped. That single upload is
essentially the whole 76 MB, and it means the BC7/BC5 pipeline is bypassed
entirely in the dev runtime.

This is the likely source of the "unreasonable GPU allocations" seen in
Instruments: not churn (measured at 0/600 frames) but magnitude.

Consequence: the 128 MB budget question is still open, because the shipped
player was never the thing being measured.
