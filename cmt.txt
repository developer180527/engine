cook: .cache garbage collection (engine_cook --gc / --gc-prune)

Cooked output accumulates: a cooker version bump re-cooks under a new key, a
deleted source leaves output behind, and a regenerated registry.db mints fresh
UUIDs so every previous file is instantly unreferenced. Measured: one version
bump grew fps_shooter/.cache from 72 MB to 113 MB, all growth orphaned.

Keep set = every registry record's cookedPath, plus its sibling .ctex files
re-derived via ICooker::enumerateOutputs (the exactness the DDC dedup already
needed), plus cooked scenes whose source .scene still exists. Sweep is an
ALLOWLIST: only .cooked/.ctex are candidates, so registry.db (+wal/shm),
anim/*.ozzclip and anything a future cooker adds survive by default. A GC that
deletes what it does not recognise is how caches eat real data.

DRY RUN BY DEFAULT; --gc-prune deletes.

THE SAFETY TEST FOUND A REAL BUG. Moving registry.db aside did NOT fail:
AssetRegistry::open() CREATES the database when missing, so the GC opened an
empty registry, concluded nothing was referenced, and deleted 8 of 9 files.
Two guards now, both verified to delete nothing:
  - registry.db absent            -> refuse (open()'s return cannot be trusted)
  - registry present but EMPTY    -> refuse (a rebuilt/mid-scan DB is not
                                     "every asset was deleted")

Reported size is LOGICAL, not disk, and the log says so: materialized outputs
are hardlinks to DDC blobs, so removing a .cache entry drops one link, not the
inode. Measured 72.7 MB of orphans removed with total disk unchanged at 55 MB.
Claiming freed disk would be a lie a user could check.

Verified: 7 orphans found and removed, second pass finds 0, game loads with 0
failures afterwards, both fail-closed paths protect all 9 files.

24/24 unit, 2/2 fuzz-regress, 2/2 docs.
