render: RenderStatsChannel — GPU handle churn, VRAM and draw budget

Instruments' graphics track showed the editor making an unreasonable number of
GPU allocations, but a platform profiler reports Metal objects, not which
engine system created them. This reports the same truth from inside bgfx, per
frame, on every backend.

The diagnostic that matters is handle CHURN, not absolute counts: a steady
scene should create and destroy nothing while the camera merely moves. Counts
rising = leak; oscillating = per-frame create/destroy; flat = the traffic is
transient buffers (ImGui, debug lines), which is by design. The channel
reports the delta and a one-line verdict.

Also the VRAM budget instrument. The target machine is an Intel UHD 630 with
128 MB shared and 4 GB system RAM, so texture + render-target memory is a hard
constraint and "graphics tuned down" needs to be measurable, not hoped for.

First measurement, fps_shooter, 600 fixed frames via engine_host --frames:
  draws avg 14.7 / max 19        (nowhere near a draw-call cliff)
  VRAM  tex 76.0 MB  rt 71.0 MB  peak 147.1 MB
  transient vb 0.2 KB/frame      (nothing)
  CHURN 0/600 frames             -> STEADY

So the RUNTIME renderer is clean — the Instruments finding is editor-specific
(ImGui suspected, not yet measured). The resize path was checked first and is
already guarded (>8px + 5 stable frames).

Two real findings instead: 147 MB peak exceeds the 128 MB target budget with a
three-mesh scene, and rt memory is 5x the naive 1280x720 figure (~14 MB
expected, 71 MB reported) — unexplained, and the highest-value thing to chase.

Lives in engine_host rather than the runtime: renderer.h and runtime.h are
compiled against poison bgfx headers by sim_purity_check, and this channel
needs bgfx. A tool has no such constraint.
