cook: shaders become assets with a machine-checked declared interface

Phase 5 of docs/renderer-audit-and-plan.md, finding R3. material.h hardcodes
five fields, so "custom material" means "recompile the engine". A material can
only become data once a SHADER publishes what a material may set — so that
comes first.

A .shader is JSON naming its .sc sources plus the interface they expose:
parameters (name, type, target uniform + float offset, defaults) and samplers
(name, uniform, stage, fallback). The cooker compiles the variant matrix per
backend profile and writes a .cshader container.

THE PART THAT MATTERS: the declaration is verified against the real compiled
shader, not trusted. bgfx's shader binary carries its own uniform table
(shaderc_metal.cpp:240-260 and the equivalent in every backend), so the cooker
compiles, reflects the truth back, and REJECTS a mismatch. Without that, a
declared interface is a JSON file that can lie — a material sets "roughness",
the value writes nowhere, and nothing reports it. Three failures caught:

  • a parameter naming a uniform the shader doesn't declare
  • a parameter whose offset runs past the uniform's registers (the tail lands
    in adjacent uniform memory)
  • a sampler declared against a value uniform, or vice versa

The reverse direction is a WARNING: u_lights, u_viewProj and u_shadowMtx are
engine-driven and legitimately not material parameters. Erroring on those would
make the check unusable; ignoring them would hide a forgotten exposure.

THE ANTI-BLOAT RULE, enforced not just documented: features are a closed list
the shader author declares, and a material selects a combination — it can never
author one. Unreal's permutation explosion, and every piece of machinery built
to survive it, follows from letting materials generate shader code. Refusing
that keeps the matrix (2^features x profiles) small enough to simply cook all
of it, with no stripping infrastructure. kMaxShaderFeatures = 8, rejected at
parse time so the rule can't erode quietly.

Cross-compilation is checked rather than discovered on the target machine.
shaderc cannot emit D3D bytecode off Windows — shaderc_hlsl.cpp:21,91 guards
D3DCompiler on BX_PLATFORM_WINDOWS, and shaderc_dxil.cpp:169-175's macOS
fallback is literally "dxcompiler???". profileCookableOnThisHost mirrors those
guards, so COOK_SHADER_PROFILES=metal,dx11 on macOS cooks metal and says dx11
needs its own runner. Silently dropping it would ship a package that renders
nothing.

Shaders go through ICooker rather than a bespoke build step so they inherit the
DDC, the thermal governor, memory-budgeted admission and .cache GC for free.
Compiles run out-of-process, matching the worker model — shaderc is a compiler
stack already excluded from the sanitizer lanes because it aborts under them
(CMakeLists.txt:179-185), and its diagnostics are captured verbatim so a broken
shader reports WHY.

One concern per file: shader_manifest (parse+validate), shaderc_invoke (one
compile), shader_reflect (read the uniform table), shader_verify (compare),
shader_cooker (sequence), assetlib/shader_asset (container).

Verified: full build clean, ctest unit 27/27 (was 26), engine_doctor 54 docs /
0 errors. Really cooking shaders/standard.shader produces 3 profiles
(metal/spirv/glsl), real VSH/FSH bytecode, interface round-tripped.
MUTATION-PROVED on a real cook: renaming u_params to u_parms in the manifest
fails the cook and names both affected parameters.

Also removes shaders/vs_triangle.sc.bak, stale in-tree.
