editor: draw over the title bar, and hand back what that takes away

The editor's menu bar now occupies the row the title bar used to. It is NOT an
undecorated window, and that distinction is the whole design: setting
GLFW_DECORATED=false / SDL_WINDOW_BORDERLESS is the obvious way to get the look
and it throws away move, resize, minimise, maximise, close, snapping,
double-click-to-zoom and the WM animations, each of which then gets
reimplemented by hand, per platform, badly. That is how editors end up with a
window you cannot resize from the top edge.

Instead the window stays fully decorated and only the bar's DRAWING is
suppressed. On macOS: FullSizeContentView + titlebarAppearsTransparent +
NSWindowTitleHidden.

── the seam ────────────────────────────────────────────────────────────────
runtime/platform/title_bar.h. Title-bar suppression reaches PAST GLFW/SDL to
the native window, so CMake selects it by OS rather than by window backend,
which is why this did not fork the two window backends. Both call the same
functions; only the editor opts in via PlatformConfig::hideTitleBar.

Games keep their title bar. The flag defaults false; engine_host and
engine_player are unchanged. A shipped game window is a normal window.

── what hiding the bar takes away, and giving it back ──────────────────────
The content view swallows the events the WM used to receive, so drag and
double-click-to-zoom stop working even though the window is still decorated.
Both are forwarded explicitly: the strip right of the menus is a drag region
calling performWindowDragWithEvent:, which asks the OS to run its own move
loop. Deliberately not "track the mouse and set the origin each frame", that
reimplementation loses snapping, drag-to-another-display and the release
animation, and fights the compositor for every pixel. Double-click reads the
system's own AppleActionOnDoubleClick preference instead of assuming zoom.

Menu-bar height and the traffic-light inset are both MEASURED from the live
window every frame, never hardcoded: the lights move with the system's
appearance and accessibility settings, their spacing has changed across macOS
releases, and the band height differs by OS version. The bar was 24px against a
28pt band, which is why it looked thin.

── Windows is not the same job ─────────────────────────────────────────────
Its minimise/maximise/close are part of the NON-CLIENT area WM_NCCALCSIZE
removes, so hiding the bar DELETES them; macOS's traffic lights survive because
they belong to the window's own chrome. Hence titleBarNeedsCustomButtons(),
true on Windows, false on macOS, and the editor draws its own buttons when it
is set. ImDrawList primitives rather than font glyphs, because the Windows
convention is Segoe MDL2 Assets and that font is absent here. 46x32 with a 10px
glyph, close red on hover: the metrics every other window on the user's desktop
already uses.

The button DRAWING is verified, the macOS build was temporarily forced into
the Windows shape to screenshot placement, sizing and spacing.

title_bar_windows.cpp itself is ⚠ UNVERIFIED and says so at the top: written
without a Windows toolchain to compile against, and no CI builds a Windows
target. WM_NCCALCSIZE with the maximised-window inset and the auto-hide-taskbar
case, WM_NCHITTEST rebuilding the top resize edge, a chained (not replaced)
window proc so GLFW's own input handling survives. Treat it as a reviewed
proposal; it is a Windows-only TU and cannot affect the macOS or Linux builds.

Linux is not implemented and falls back to a real title bar. Whether one exists
at all is the compositor's call, server- vs client-side decorations differ
across GNOME, KDE and wlroots, so there is no portable call to make.
