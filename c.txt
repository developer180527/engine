tests: pin the mesh dedup, one cooked mesh, one pair of GPU buffers

The dedup fix was unpinned, so it could regress silently, and its failure mode is
exactly the kind that does: nothing crashes, the scene just renders 8% of itself and
the error text blames the files instead of the handle pool.

tests/mesh_dedup_test.cpp. Real cooked meshes (MeshCooker on a tiny OBJ), real
AssetService, bgfx Noop, no project assets required, so it runs in CI.

IT LOADS ONE PATH 5 000 TIMES: past BGFX_CONFIG_MAX_INDEX_BUFFERS (4096), on
purpose. A test that loaded twice and checked the handle matched would pass against a
broken implementation; this one reproduces the production failure.

Ten assertions, three cases:
  * the regression: 5 000 loads all succeed, all return the SAME handle, create
    exactly one buffer pair, and leave one mesh in the registry;
  * the negative case: a DIFFERENT cooked path gets its own handle and its own
    buffers, so dedup is by path and not 'always return the first mesh'. Without this,
    a constant-handle implementation passes everything above;
  * failure isolation: a missing cooked file yields an invalid handle, allocates no
    buffers, and does not poison a later good load of a valid path.

MUTATION-CHECKED. Removing the dedup early-return reproduces the original bug with the
original numbers: 907 of 5 000 handles invalid, vb 3 -> 4096 (pool capped), 4 093
meshes in the registry, and the different-path case collapses to handle 0 as well. Six
of ten assertions fail. It fails in the SHAPE of the real defect, not merely with
different numbers.

Buffer counts are read after bgfx::frame(), because getStats() reflects the last
SUBMITTED frame and destroy() is deferred to submission, the same trap that made
render_registry_test once report a leak that did not exist.

Two doc gates fired and are handled in the same commit rather than left to break the
docs test: runtime/docs/info.md cites this test as the pin (with the mutation numbers),
and plugins/info.md was stale from the audio change, it now records the async device
start and, more importantly, that onDetach waits on that job so EngineRuntime::shutdown
must keep detaching plugins BEFORE jobs::shutdown(). Do not reorder those two.
