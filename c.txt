api: expose the primitive tier: jobs, memory, draw submission

The table exposed the engine's SUBSYSTEMS: physics, animation, nav, audio.
Those are finished opinions. A developer who wants their own animation system
cannot build one out of them, they can only adopt ours or fork the engine.

These three are the layer underneath, so our animator becomes the DEFAULT
implementation rather than the only one:

  jobs       the engine's own worker pool. A kit spawning private threads
             competes with the pool already saturating the machine.
  memory     tagged heaps + the frame arena, so kit allocations are visible to
             the budget telemetry instead of hiding inside malloc.
  drawSubmit geometry with no entity and no component, cleared at the flip,
             pixels for a system the engine never modelled.

── decisions that are not arbitrary ────────────────────────────────────────
NO JOB HANDLES in v1. A handle crossing a module boundary means the module
owns a lifetime the host allocated, and a kit unloaded mid-job takes the
process with it, the engine already fixed one JobHandle use-after-free of its
own (C.5). Blocking parallelFor covers the data-parallel work kits actually
have; async appends in v2, which is what per-group versioning is for.

A DISABLED jobs group runs the work INLINE rather than dropping it. A kit whose
parallelFor silently no-ops would skip a whole pass and present as a logic bug
somewhere else entirely. Degradation costs throughput, never correctness.

drawSubmit is published UNCONDITIONALLY and no-ops without a renderer, instead
of going absent like ui does. A kit that draws must run unchanged on a
dedicated server; making the group disappear would force every such kit to
branch on capability. Submissions take bounds from the mesh, so they are
frustum-culled like anything else, bypassing the cull would mean lying about
bounds, which is the right amount of hard.

Submitted draws are appended per VIEW and cleared in frame(), not at
extraction: every view built this frame must see the same submissions, and
clearing at extraction would hand the game view an empty list whenever the
scene view extracted first.

── three bugs found while doing it ─────────────────────────────────────────
eapiGuard had `static bool warned[7]` against nine groups: nav and draw wrote
PAST THE END on their first failure. Now sized from the enum, so appending a
group cannot reintroduce it.

engineMemFrameAlloc had no boundary check. FrameArena::alloc SPILLS TO THE HEAP
on overflow, right for engine code that overshoots by a little, wrong across a
module boundary where a kit's bogus size (its own integer overflow, an
uninitialised local) makes the HOST attempt the allocation. Asking for a
terabyte now costs a null. Found by writing exactly that test and watching the
machine try to serve it.

A structSize mismatch reported "module was never bound (old host?)", blaming
the host when the MODULE is the stale half. It now names the mismatch, prints
both sizes, and says to rebuild the module. Hit this myself the moment the
table grew; every kit author will hit it on every append.

── consequence to plan for ─────────────────────────────────────────────────
Appending bumps structSize, which rejects every module built against the old
table: all three Kits and the game module needed a rebuild. That is the
documented contract working, but it makes table growth a coordinated release
across repos that share no build. Batch API additions into deliberate versions
rather than appending ad hoc.

tests/api_primitives_test.cpp pins the contract a kit depends on: parallelFor
covers [0,count) exactly once at awkward counts and grains, is safe under
concurrent entry, tagged allocation is visible to the telemetry, frameAlloc
refuses over-capacity, and submitting with no renderer is a no-op. Sized for
edges rather than magnitude, the first draft swept to 65 536 across 12 grain
combinations and turned a unit test into a stress run.

65 tests pass. fps_shooter runs with every group bound.
