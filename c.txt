input: the header that linked GLFW into every build, including the SDL3 ones

engine_runtime linked GLFW unconditionally, in both window backends. The cause
was one line: input_system.h did `#include <GLFW/glfw3.h>` and branched on
ENGINE_WINDOW_BACKEND_SDL3 in six places. Because input.h, input_map.h,
input_sources.h, runtime.cpp and the editor all include that header, a single
include decided the link line for the whole engine — an SDL3 build linked GLFW,
and so did a host that supplies its own window. A Qt or Rust editor dragged in a
windowing library it had no use for, which is exactly the vendor-lock the SDK
exists to avoid.

It was also the ONLY header in the tree leaking a window library. Everything
else was already isolated in backend TUs, which is why this reads as one knot
rather than a sweep.

── the seam already existed ────────────────────────────────────────────────
wsi:: (hoisted out of src/editor/ last commit) was already 80% of what the
input source needed — isFocused and cursorPos were sitting right there. So this
extends that seam rather than inventing a second abstraction beside it:

  pollKeyboard / pollMouseButtons   bulk, writing into the ENGINE's code space.
      Per-key isKeyDown would be ~350 out-of-line calls per frame, which makes
      the input system's per-frame cost a property of how the seam is compiled.
      That is the wrong thing to leave to a linker.

  InputSink / installInputSink / feedNativeEvent
      Scroll and text — the two inputs NEITHER backend can poll, and therefore
      the entire reason that #ifdef existed. GLFW delivers them as callbacks and
      SDL as events; both reduce to "call me when this happens", so the sink
      reconciles them and no consumer learns which it is behind.

Text crosses as CODEPOINTS, because GLFW's char callback already provides them.
The SDL backend's UTF-8 decode moved into window_ops_sdl3.cpp where it belongs,
so no consumer ever sees an encoding.

The GLFW/Key static_asserts moved to window_ops_glfw.cpp. They are a claim ABOUT
THE GLFW BACKEND, and asserting them in the one TU that relies on the
equivalence is both more accurate and free of consequence for everyone else —
whereas stating them in a shared header is what forced that header to include
GLFW in the first place.

input_system.h: 289 -> 158 lines, zero #ifdef, no backend named anywhere except
in comments. There is now a note at the top saying why that matters, because the
next person to add an #include there would silently re-couple every consumer.

── proven, not asserted ────────────────────────────────────────────────────
Stashed the change, reconfigured, read the link line:

  BEFORE  SDL3 build, engine_player link line:  libglfw3.a
  AFTER   GLFW build: libglfw3.a      SDL3 build: absent

Zero undefined glfw symbols in the SDL3 engine_runtime. Each windowing library
is now reachable from exactly two TUs — its IPlatform and its window_ops — both
already selected by the one CMake branch that picks the backend.

── a landmine defused rather than reproduced ───────────────────────────────
Moving the chained callbacks into file-statics meant a second installInputSink
on the same window would store OUR OWN function as the one to chain to, and the
next scroll event would recurse until the stack ran out. Not reachable today
(the editor calls init() once, and there is no project close/reopen cycle) and
the same latent shape existed before. But the failure mode is a stack overflow
far from its cause, so it is guarded: keep the original previous callback if
GLFW hands back our own.

── verification ────────────────────────────────────────────────────────────
Both backends build clean. GLFW ctest 72/73; SDL3 unit lane the same single
failure — kit_lifecycle_test, which wants Kit .so files from separate gitignored
repos and failed before any of this. input_test and input_config_test pass.
Docs gate 0 errors, warning set unchanged.

── what this finishes ──────────────────────────────────────────────────────
docs/architecture/extension-model.md §4b now says the SDK offers a host three
things independently: a GPU-free layer for tools (engine_core), a runtime that
links ONE windowing library of its choosing, and a per-window seam for driving
more than one window. None of them requires ImGui, and none requires the editor.

The custom-editor story has no remaining structural blocker.

Related, and now a smaller job than it was: gamepads still do not reach the raw
HID path (HidSource::init passes {.gamepad = false}, pending curation, backlog
#13). The window/input coupling that tangled it is gone.
