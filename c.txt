audio: miniaudio moves behind the ABI, and the suite catches the first real bug

The seam is live. src/plugins/audio_plugin.h no longer contains the word
ma_engine; the engine's only remaining reference to miniaudio is one line in
audio_host_services.h naming an entry point. Replacing it with an FMOD adapter
or a Rust spatial engine is now a change to which table that line asks for.

── the same source, built twice, on purpose ────────────────────────────────
engine_audio_miniaudio          linked into the engine (no dlopen in a game)
engine_audio_miniaudio_module   a standalone .so the Rust suite dlopens

The conformance lane now runs against the MODULE, so it tests the code the game
actually runs rather than something written to pass it. And the module build is
not redundant — it is the proof: it links CoreAudio, CoreFoundation,
AudioToolbox and libc++ and NOTHING ELSE, exporting exactly one symbol. Add an
engine header to that file and it stops linking. "The provider is
engine-independent" stopped being a claim in a doc.

── the suite earned its keep on day one ────────────────────────────────────
The first version let ma_engine create its own device, so samplesPlayed came
from ma_engine_get_time_in_pcm_frames. That is the NODE GRAPH's clock: it
advances only while something is mixing, and sits frozen at 0 otherwise. The
run failed with

  FAIL  the sample clock and the host clock agree on elapsed time
        (0.0 ms of samples vs 125.2 ms of host)

which is precisely the bug that assertion was written to find, one commit after
writing it. As a device clock it was unusable and nothing else would have
noticed.

The fix was to honour the ABI's own central claim — THE PROVIDER OWNS THE
DEVICE — by passing our own ma_device. Three contract obligations fell out at
once: samplesPlayed became a real free-running clock, callbackOverruns became
measured instead of hardcoded 0, and desc->bufferFrames is finally honoured.
(miniaudio's comment on its pDevice field names a "ma_engine_data_callback"
that is not a public symbol; ma_engine_read_pcm_frames is what its internal
callback actually calls.)

── preserved deliberately ──────────────────────────────────────────────────
mem::Tag::Audio. The old code pointed miniaudio's allocation callbacks at the
audio heap with hardcoded lambdas. The provider now receives that heap through
host services, so the tagging travels THROUGH the ABI instead of around it —
which is what makes it survive swapping the backend.

The device still does not start on the main thread. Sampling startup put 585 of
1722 main-thread samples — 34%, ~536 ms — blocked inside CoreAudio's
HALB_IOThread::StartAndWaitForState. create() runs on a job, m_ready gates
everything, and nothing on screen ever depended on an audio device.

── better for free ─────────────────────────────────────────────────────────
The old path called ma_sound_init_from_file per play: every gunshot reopened
and re-decoded the same file. Sounds are cached by path now, so a repeat play
costs a voice instead of a decode, and one decoded sound feeds 8 concurrent
voices from a single copy of the samples. Large files go through createStream,
so nothing big is ever resident — the old code streamed too, but only because
miniaudio was doing the file I/O itself.

Nothing allocates once the device is running: fixed-capacity sound and voice
arrays in one block taken at create(), with index+generation handles so a stale
id is REJECTED rather than rebound to whatever reused the slot. The engine
legitimately sends stale voice ids — a voice can end between frames — so that
is correctness, not tuning.

── the suite only ever fed it garbage ──────────────────────────────────────
Every existing assertion checked that a provider says NO correctly. A backend
that rejected every sound in existence would have passed all of them. So
run_playback builds a WAV sine by hand and drives all three resource paths:

  ok  a valid WAV is DECODED, not rejected
  ok  the device clock advances while audio plays (0 -> 4096)
  ok  one decoded sound supports concurrent voices (8/8)
  ok  an F_STREAM sound plays from the engine's buffer
  ok  createStream actually CALLED the engine's reader
  ok  memory returned through host free (40 allocs, 40 frees)

48 assertions against the real provider — 33 contract, 15 playback.

── verification ────────────────────────────────────────────────────────────
Full build clean; ctest 71/72. The failure is kit_lifecycle_test wanting Kit
.so files from separate gitignored repos, failing before this work too. Docs
gate 0 errors.

── still not done ──────────────────────────────────────────────────────────
updateEmitters and setListener are implemented on both sides, but the engine
does not drive them from the scene: sounds still play at fixed positions with
the listener at the origin. That is engine-side work, not ABI work, and the
guide says so rather than reading as finished.
