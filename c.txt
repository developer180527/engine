cook: the DDC grew forever and a truncated worker result read as success

Two external reviews of the DDC/cook system, triaged claim by claim against the
code in modules/assetlib/src/issues.md: 7 fixed, 8 real-and-open, 3
misdiagnosed, 7 rejected. Recording the rejections is half the point, several
were plausible and wrong, and the next reader should not re-derive that.

THE TWO THAT MATTERED

DDC eviction. --gc (d121a93) does not cover this store: it reconciles a project
.cache/ against its registry, while DDC keys derive from INPUTS, so every source
edit, cooker bump or settings change mints a new key and orphans the old blob
with no referrer left to notice. Reference counting cannot collect that. Worst on
the shared tier, which accumulates every blob every machine ever produced.
DdcStore::collectGarbage(maxBytes, prune) evicts LRU by mtime, which fetch now
touches on a local hit so the order reflects USE and not ingest. Three decisions:
a blob hardlinked into a live .cache is PINNED and never evicted (unlinking the
store's copy frees ZERO bytes, the project's link keeps the inode, and would
re-ingest something in active use; counting it as reclaimable would make
freedBytes a lie); the DDC pass runs AFTER the cache sweep, because those
deletions drop hardlinks and un-pin blobs, so --gc-prune frees real disk in one
invocation instead of two; and the SHARED tier is never collected from a client,
because no client can know what another machine still needs and one over-eager GC
costs the studio a recook. ENGINE_DDC_MAX_MB, default 20 GB, 0 = unbounded so it
is opt-out rather than a cache that deletes itself.

Worker result framing. RESULT ok is the FIRST body line, so a worker killed
mid-write (deadline SIGKILL, rlimit OOM, signal from a corrupt parse) left a file
that parsed as a clean SUCCESS with its OUTPUT lines simply absent, and the
asset committed without its sibling textures. That is the silently-untextured
build (cf. ab77845) arriving through the IPC channel instead of the packager. Now
framed with a magic/version header and an END <lines> <digest> trailer, validated
before any field is read. assetlib/cook_result_file.h is ONE implementation
shared by writer and reader, which were previously two hand-rolled halves of a
protocol documented only in comments. FNV-1a not BLAKE3 on purpose: this detects
truncation, the file sits in our own temp dir beside the artifact it describes,
and anyone who can rewrite it can rewrite that artifact, the DDC content hash
guards the artifact itself.

ALSO FIXED

- Migrations: every SQLite error was discarded, migrate() returned void and
  open() returned true regardless, so a corrupt or read-only registry reported
  success and then silently recorded nothing. Now only the exact "duplicate
  column name" is benign; open() fails on anything else. PRAGMA user_version
  added, which also refuses a database written by a NEWER build rather than
  writing to it and dropping columns this build cannot see, which matters
  precisely when a cache is shared across machines on different builds.
- ::stat(p.string().c_str()) -> std::filesystem. path::string() renders the
  native NARROW encoding (ANSI code page on Windows), so a source file with a
  non-ASCII name never round-tripped and statChanged reported "changed" forever
 , recooking it on every scan, permanently. One-time cost: the first scan after
  this rehashes everything once (mtime representation changed), then nothing
  recooks because the hash matches.
- POSIX memory cap now applied by the parent between fork and execv. rlimits are
  inherited across exec, so it predates the child's first instruction including
  static initializers; applying it in the worker's own main() from argv left all
  of that uncapped. This gives POSIX the property Windows already had (job object
  assigned while the process is suspended). posix_spawn cannot express it, POSIX
  has no rlimit spawn attribute, hence fork/exec. Exit code 66 now reports
  "cannot exec the worker" instead of looking like a crashed cook.
- findBySourcePath per scanned file was O(N) statement COMPILATIONS, not just
  queries (it concatenates SQL and prepares every call). Folded into the snapshot
  hashIndex() already builds in the same function. Not claimed as a speedup:
  unmeasured at scale, and warm no-op is ~37 ms on fps_shooter (2026-08-03).
- MemGovernor asserts on an unbalanced release. The clamp keeps a release build
  scheduling; it does not make the imbalance correct.

WHERE THE REVIEWS WERE WRONG

"Migrations skip silently after a failure", the cascade cannot happen; each is
its own exec in a loop. "settingsFingerprint fails -> empty key", it does not;
MaterialCooker encodes failures as DISTINCT fingerprints and self-heals.
Merkle-DAG keys rejected as the wrong shape: MaterialCooker hashes only the
.shader manifest and not the .sc sources on purpose, so a recursive fold would
recook every material in the project on every shader edit. cgroups and
posix_spawnattr_setflags rejected (the latter does not exist as a mechanism).
Hardlink locking / ETXTBSY rejected: blobs are content-addressed and immutable,
so nothing is ever updated in place, and ETXTBSY is for executables.

BIGGEST FINDING, IN NEITHER REVIEW (open, O1)

Two dependency-invalidation mechanisms exist and NEITHER is wired:
DdcKeyInputs::depHashes is hashed by computeDdcKey but populated by nobody, and
dependents()/transitiveDependents() are correct but never called from the cook
path. Harmless today only because settingsFingerprint covers the one real
multi-input cooker. The hazard is a future contributor assuming invalidation
works because finished-looking plumbing is sitting there. Recorded as an
unenforced CONVENTION rather than a missing architecture: the fix is a test
asserting each cooker's key changes when each declared input changes.

EVIDENCE

tests/cook_hardening_test.cpp, framing (truncation after the verdict,
mid-trailer, digest mismatch, dropped line, unframed legacy, empty), DDC GC
(LRU-not-FIFO via a fetch that promotes the oldest blob, dry run changes
nothing, pinning, budget 0 = unbounded), schema versioning (forges user_version
by patching bytes 60..63 of the SQLite header, so no sqlite3 dependency and no
widening AssetRegistry's private API for a test). Mutation-proved: reverting
unframe to pre-fix behaviour fails 8 assertions.

No test covered the child-process spawn path at all, so fork/exec was verified
by hand: a real shader cooked out-of-process in 1780 ms through the new spawn and
framing, and --gc / --gc-prune reporting checked against a real store.

32/32 unit, 2/2 fuzz-regress, 2/2 docs. Both hardened docs updated with content
before committing, since engine_doctor compares verified: against git and so
cannot see uncommitted work, green before a commit is not green after it.
