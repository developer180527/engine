render: extraction 15.2 -> 1.1 ms, and the bottleneck is no longer here

Four changes at 20 000 objects, each measured before the next:

  15.2 ms  start
   9.7 ms  partitioned + optional query terms (previous commit)
   8.0 ms  Transform::getMatrix composes SRT directly
   6.6 ms  SkinnedMesh as an optional term too
   1.1 ms  chunked extraction on jobs::parallelFor

getMatrix WAS DOING TWO FULL 4x4 MULTIPLIES, 128 multiplies, 96 adds, to compose
an SRT where S is diagonal and T is the identity with one row replaced. Three
quarters of that arithmetic was against structural zeros. Written out directly it is
the same 16 floats. It is the most-called function in the engine (every entity every
frame, plus physics sync, animation, gizmos), so it is verified rather than
eyeballed: BIT-EXACT against the two-multiply reference over 2 000 randomised
transforms incl. negative, non-uniform and zero scale (worst element delta 0.0), and
the m[12..14] == position contract the gizmo depends on is asserted separately.

SkinnedMesh was the last per-entity try_get in the loop, worth ~1.4 ms, but the
bigger effect is that the per-item body now touches NO ECS handle, only component
arrays. That turned the parallel step from an argument about flecs thread rules into
an argument about disjoint slices.

CHUNKED JOBS: extraction slices each archetype into 512-item ranges of contiguous
arrays, walking TABLES, so 20 000 objects in one archetype is a few dozen chunks
rather than 20 000 iterations, then parallelFor fills disjoint slices of a pre-sized
m_items. Missing meshes leave gaps that a compaction pass closes, skipped entirely
when nothing was dropped (every normal frame).

ONE BODY serial or parallel. Below 2 048 items, or with no job pool (headless tools,
tests), the same extractChunk runs in a loop. Two implementations would mean tests
exercise one and the engine ships the other, and the drift would be invisible.

Partially retires the runtime's 'single-threaded frame orchestration' tradeoff,
engine::jobs over extraction was its stated trigger.

SIMD WAS NOT WRITTEN, AND SHOULD NOT BE NEXT. The frame's cost has left the
renderer. At 50 000 objects the frame is 34.3 ms, of which the whole render path is
8.6 (extract 2.6, cull 3.9, shadow 1.8, submit 0.3) and ~25 ms is Sim.prevSnapshot,
a deferred structural set<PrevTransform> per entity per fixed step, plus a
has<Camera>() pair lookup each. It had NO PROFILER ZONE, which is why it has been
invisible. It has one now, and is recorded as src/runtime/docs/issues.md H.0 with a
staged fix. Hand-optimising extraction further would be optimising a quarter of the
problem. Cull is also now the larger render phase at scale.

VERIFIED: submit counters byte-identical serial vs parallel at 1 k / 5 k / 20 k /
50 k, and those counters depend on every matrix, because culling reads them. 50/50
ctest. Render + sim tests pass under ASan.

NOT sanitizer-verified at scene scale: ASan on the windowed host runs ~13 s per frame
here, so that run was abandoned rather than left burning. Standing behind the parallel
path instead: identical counters, a debug assert on the slice arithmetic, and a body
that only does const registry reads and disjoint writes. A TSan lane over a scene
this size is still missing.

src/core/info.md re-verified, it is hardened, transform.h made it stale, and the doc
gate caught it. issues.md R15 added, R14 and info.md corrected where they still
quoted the old numbers.
