runtime: real cooked assets never used the cooked path, and never deduped

A layered fuzz generator over real cooked assets (scripts/gen_fuzz_scene.py, seeded,
drawing from the Medieval Village MegaKit's 176 cooked models) found two bugs in its
first 200 objects. Both were invisible to every stress scene to date, for the same
reason: those scenes use engine://primitive/cube, which is ONE shared mesh loaded
through the primitive path.

BUG 1: THE COOKED FAST PATH NEVER WORKED. entity_serializer joined cookedPath to
ctx.projectRoot, producing '<project>/meshs/<uuid>.cooked'. The cache is at
'<project>/.cache/', and AssetService::loadMesh already resolves RELATIVE paths
against it, exactly as its doc says, so the pre-join defeated the resolution and
every cooked mesh load failed, silently falling through to the Assimp source
importer. Nothing looked broken: scenes still rendered, just via the slow path. A
shipped dist with no source assets would have failed outright. Fixed by passing the
path through relative.

BUG 2: NO MESH DEDUP, SO bgfx's BUFFER POOL RAN OUT. Sync loadMesh created a new
vertex+index buffer pair per CALL. With 50 000 entities referencing 176 distinct
cooked meshes:

  bgfx buffer creation failed   45 911  ->  0
  meshes loaded                  4 089  ->  176

4 089 is BGFX_CONFIG_MAX_INDEX_BUFFERS (4096) minus the primitives, the count was
the giveaway that it was the handle pool and not the files. 92% of the scene silently
did not render.

The cause was structural, not a missing memo: the path->handle map lived inside
AsyncState, which ensureWorker() creates LAZILY, so a purely synchronous scene load
never had a cache at all. Moved onto AssetService, next to m_texCache, which sits at
exactly that level because textures had this identical bug ('every load of the same
cooked texture uploaded ANOTHER copy to the GPU', renderer audit R1). Meshes simply
never got the same treatment. One cache per resource kind, shared by both paths, so a
sync and an async load of the same path cannot each create buffers.

WHAT THIS REFRAMES. With real content, INSTANCING DOES NOTHING, 0 instanced submits
at 200 objects and at 50 000. Meshes with submeshes are excluded by construction and
this kit averages ~1.7 material groups per mesh (80 have 1, 71 have 2, 23 have 3, 2
have 4). At only 4 089 items the pipeline submitted 3 067 draws and DROPPED 534 at the
uniform-buffer ceiling, with 3 067 material binds for 3 067 draws. So '20 001 objects
-> 1 draw call' was a best case real content cannot reach, and R7 (material-bind
dedup) stops being cosmetic.

Measured with real assets: 5 000 objects 11 ms/frame, 10 000 objects 14 ms/frame,
both hitting the draw ceiling.

NOT ESTABLISHED, and stated rather than guessed: 50 000 objects runs at >18 s/frame,
wildly superlinear against 10 000's 14 ms. Undiagnosed. A 20k/30k bisect separating
boot+load from per-frame is what would localise it; that run is what had to be
abandoned, which is weak evidence the cliff sits at or below 20k. No claim is made
about whether it is GPU, VRAM or scene-load.

ALSO MISSING: no regression test pins the dedup. 'N entities sharing one cooked mesh
create exactly one buffer pair' is cheap to assert on bgfx Noop via getStats(), and
without it this can silently come back.
