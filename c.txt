runtime: startup 2.60s -> 1.16s, the main thread was waiting on an audio device

Profiled rather than guessed. `sample` on engine_host fps_shooter --frames 1, 1 722
main-thread samples:

  953 (55%)  kit dlopen, KitHost::loadKit -> dyld mapSegments -> fcntl
  585 (34%)  AudioPlugin::onAttach -> ma_engine_init -> ma_device_start -> BLOCKED

FIXED: THE AUDIO BLOCK. All 585 samples were a WAIT, not work, the main thread sat in
CoreAudio's HALB_IOThread::StartAndWaitForState while an audio device spun up, before
the first frame could be drawn. Nothing on screen depends on that.

ma_engine_config::noAutoStart makes ma_engine_init return without starting the device,
and the start now runs on a job. m_ready flips only once the device is actually live, so
a sound requested during that window no-ops exactly as it would have if audio had
failed, every entry point already guarded on it. Silent audio for a fraction of a
second beats a stalled boot, and that is where a game shows a logo anyway.

onDetach waits on the start job before ma_engine_uninit, or shutdown would race a device
coming up and tear down under it. Safe because EngineRuntime::shutdown detaches plugins
BEFORE jobs::shutdown(), verified, not assumed; it is the same ordering Jolt's job
adapter already depends on.

Measured: 2.60 s -> 1.16 s (first run 1.99 s, then 1.16, 1.16).

TWO OF MY OWN GUESSES CORRECTED, recorded so they are not re-litigated:

  I suspected the editor re-cooked shaders on every start, having seen '6 shaderc
  invocations' in the first profile. It does not. Running the editor twice shows ZERO
  invocations both times, that cook was a one-time cold event after my engine rebuilds,
  because the cook key includes engine state. The DDC is working.

  The editor is ~1.0-1.5 s warm. Whatever 'takes ages' refers to, it is not the warm
  path; the most likely candidate is the legitimate first-launch-after-rebuild re-cook.

STILL OPEN: the kit dlopen is now the MAJORITY of startup, ~950 ms in dyld dominated by
fcntl (code-signature validation / page mapping), so most of it is not ours to
optimise. Two things worth knowing before anyone tries: it is triggered by
startSimulation, so in the EDITOR that cost moves to pressing Play rather than boot, and
several kits would multiply it. Revisit with a signed-vs-unsigned dylib measurement, not
by guessing.

NOT A BUG: the glTF fallback. Three main.scene meshes have uuids absent from the
registry (a stale cook), so the source importer correctly takes over. Re-cooking the
project removes those 173 samples.
