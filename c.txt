build: an operator new that under-promised, and a guard only one platform checked

Both Windows CI failures. Neither was a Windows quirk, both were real bugs
that three green platforms were hiding, and both are now reproducible and
mutation-proven from macOS.

── BUG-0028: THE REPLACEMENT operator new BROKE ITS OWN GUARANTEE ──────────
animator_system_test segfaulted on Windows x64 and passed on Linux x64, macOS
arm64 and Windows arm64.

`operator new(size_t)` in mem_counters.cpp requested alignof(std::max_align_t).
The standard requires it to return storage aligned to
__STDCPP_DEFAULT_NEW_ALIGNMENT__, and those are NOT the same number:

    macOS arm64    max_align_t  8    required 16
    MSVC x64       max_align_t  8    required 16
    Linux x86-64   max_align_t 16    required 16

libc++ and MSVC's STL route a type through the ALIGNED operator new only when
alignof(T) > __STDCPP_DEFAULT_NEW_ALIGNMENT__. A 16-byte-aligned type is
therefore NOT over-aligned: it takes the plain overload and relies on exactly
the guarantee this replacement was quietly breaking. Every
std::vector<ozz::math::SoaTransform> came back 8-byte aligned, and ozz writes
those with _mm_store_ps, which faults.

That explains all four legs. Linux x64 got 16 from max_align_t by luck of the
ABI; both arm64 legs tolerate unaligned NEON stores; only MSVC x64 combined a
small max_align_t with faulting SIMD.

Verified independently that mem::alloc and the ALIGNED operator new both honour
alignment correctly, the defect was the value being passed, not the allocator.

The diagnostic that found it is permanent. AnimatorSystem::Ctx::ensure now
asserts all four ozz buffers are 16-aligned and aborts naming the buffer and its
address, because the alternative is a bare SEGFAULT with no stack on one
architecture. It fires on macOS too: the bug was always on this machine, arm64
just tolerated it.

── BUG-0029: "WINDOWS HOSTS DO EVERYTHING" WAS TRUE OF x64 ONLY ────────────
cooked_format_conformance failed on Windows arm64 with "Unable to load DXC
compiler", the whole shader cook, so every shader in the project, on that
architecture only.

The D3D compilers bgfx vendors are PREBUILT x86-64 binaries, d3dcompiler_47.dll,
dxcompiler.dll and dxil.dll all report PE32+ x86-64, and a native arm64 process
cannot load one, because the emulator switches whole processes, not libraries.
The Linux branch already carried exactly this arch test, written for the
identical reason; this branch was never updated alongside it.

WHY IT REACHED CI IS THE PART WORTH KEEPING. profileCookableOnThisHost answers
for the host it was COMPILED for, so every branch is invisible to a test running
anywhere else, and only the macOS branch had assertions. The one platform whose
answer was wrong was the one with nothing checking it.

So the rule is now a pure function over (os, arch) and the host entry point is a
one-line call into it, asserted to agree. A 14-row table covers every
combination from any machine, including that an out-of-range profile id is never
cookable. Mutation FROM macOS: restoring "Windows hosts do everything" fails
"win arm64 dx11" and "win arm64 dx12"; reverted, it passes.

── ON THE CI SIGNAL ITSELF ─────────────────────────────────────────────────
Both runs reported SUCCESS. Both Windows legs are experimental: true, so a red
job sits inside a green run, which is the right setting while a platform is
being brought up, and worth knowing is the reason these two sat unexamined.
