docs: a gate you could not see until you had already pushed

The Docs workflow failed on the previous commit while CI went green. One error,
and the gate was right, I changed src/core and never re-verified its doc.

── BUG-0031: THE DOC DESCRIBED THE OPPOSITE OF THE CODE ────────────────────
So the doc got re-read rather than date-bumped, and it was wrong, not merely
stale. src/core/info.md said mem_counters "COUNTS + forwards to malloc/free;
never pools, ASan/leaks keep working", gated by ENGINE_MEM_COUNT.

ENGINE_MEM_ROUTE defaults to 1. The default build routes every allocation into
the tagged heaps, the opposite of "never pools". Forwarding to malloc is the
ENGINE_MEM_ROUTE=0 path the root CMakeLists sets automatically under heap
sanitizers; the doc described the fallback as though it were the default.

It now also states the alignment contract, which nothing described before and
which BUG-0028 turned out to hinge on entirely.

That is the staleness flag doing its job: it pointed at a doc, and the doc was
wrong. Bumping the date would have silenced the one signal that found it.

── BUG-0030: THE CHECK COULD NOT BE OBSERVED BEFORE THE COMMIT ─────────────
Staleness compared `verified:` against `git log -1` over the covered paths, and
a change sitting in the WORKING TREE is invisible to git log. So the sequence is
always: edit src/core, run check, it passes because the edit is not in history
yet, commit, now it is, push, CI fails on a doc that was already stale when
you looked.

A guaranteed round-trip for every commit touching a `hardened` subsystem without
a doc bump. It just cost one.

last_change now treats a dirty covered path as changed TODAY: the same answer CI
gives a minute later, delivered while it is still cheap. Verified by editing
modules/assetlib (hardened, verified one day earlier), "code 2026-08-27 >
verified 2026-08-26" appears locally and clears on revert. CI is unaffected: it
checks out a clean tree, so nothing is ever dirty there. Bumping `verified:` in
the same edit makes the dates equal and the rule is `code > verified`, so the
intended workflow passes.

Same SHAPE as the docs_status_current fix, arrived at from the other side. That
one was a GENERATED file gated on content the commit itself changed; this is a
HAND-WRITTEN file gated on history the commit itself creates. Both times the
check was correct and the timing made it unobservable.
