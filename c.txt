── THE FOUR THAT WERE NOWHERE ELSE ─────────────────────────────────────────
This is the finding. Four complete defects, mechanism, cause, fix, recorded only
as prose in a file nothing checks, with no id, no `pinned-by`, and no way to ask
whether their fixes had regressed.

BUG-0040. audio_provider_asan_test tracked live blocks in an unsynchronised
std::map while the ABI EXPLICITLY permits the provider to allocate off the game
thread, it is handed parallelFor and told to decode there. TSan reported races
inside libc++'s red-black tree. The fixture was the racing party, and a corrupted
tree would eventually have surfaced as "the provider freed a pointer we never
handed out": the fixture accusing the code it was written to vindicate.

BUG-0041. `verified:` dates from a UTC+5:30 machine read as the FUTURE to a UTC
runner, a hard error, on the gating leg, for a timezone, five and a half hours a
day.

BUG-0042. render_status computed staleness a shallow clone cannot know, while
check_docs already refused to and is_shallow()'s own docstring says "refusing to
make the claim beats emitting confident nonsense". Two halves of one tool
disagreeing about what it is allowed to know; ⚠️ on twenty rows that were not
stale.

BUG-0043. The cooked-format test checked status.success(), but the worker returns
`f.good() ? 0 : 65`, the exit code says whether the RESULT FILE was written, not
whether the cook succeeded. The test asked "did the worker run?" while believing it
asked "did the cook succeed?", and the machine-readable answer sat in a file three
lines away. It PREDATES BUG-0032 and BUG-0033, which is why the Add-on protocol's
rule 3, "exit status says whether the tool ran, never what it decided", is
written the way it is. The rule was learned here first and not written down.

── WHY THE FILE ROTTED ─────────────────────────────────────────────────────
The ledger has a lifecycle: found -> fixed -> pinned-by, and `status:` now
enforces it. This file had none. Things went in and nothing ever left, so "Open"
stopped meaning open somewhere around item 15, and once a list is half untrue,
the untrue half is invisible, because nobody re-reads a list they already know is
mixed.

Three rules are now stated in it, each the direct cause of one of the categories
above:

  1. Fixed goes to the ledger, not here. Four defects sat only in this file
     because that was never written down.
  2. Nothing is duplicated from the ledger. Eight items described a defect that
     already had a number and a test; when two records of one defect drift,
     nothing says which is true.
  3. An item that turns out to be FIXED is a finding. "CI has never run the unit
     lane" survived here long after ci.yml grew `ctest -L unit`, and the item's
     own text contradicted itself, calling the sanitizer job "the first lane in
     the project's history to execute ctest -L unit".

Plus an optional schema, since / where / trigger, where `where` gets the same
existence check the ledger's does, and an item with no trigger is a complaint
rather than scheduled work.
