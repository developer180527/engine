api: a kit built for v1 must run on v5, and it could not

The table's whole purpose is binary compatibility across engine versions, and
the client shim gated on exact equality:

    structSize != sizeof(EngineApiTableV1)   -> reject the ENTIRE table
    have == want                             -> reject the group

So every append invalidated every module built before it, wholesale. Adding
jobs/memory/drawSubmit this week forced a rebuild of all three Kits and the
game module. That is the opposite of the promise.

Both are now ">=": a NEWER host satisfies an older module; only an older host
is refused, which is correct because its table really is too short to read.

── ">=" ALONE WOULD HAVE BEEN DANGEROUS ────────────────────────────────────
Found while implementing it, and it changes the contract.

Groups are stored INLINE, so a group's size determines every later group's
OFFSET. Appending a field to `core` moves input, assets and draw, and an
older module, computing those offsets from its own smaller headers, would read
the WRONG FUNCTION POINTERS. Silently. The old "!=" gate was accidentally
protecting against exactly that by rejecting everything.

So the rule is stricter than "append and bump":

    A SHIPPED GROUP IS FROZEN. New functionality goes in a NEW GROUP at the
    end of the table.

That moves only structSize, which is precisely what old modules may ignore.
ENGINE_API_FROZEN static_asserts every group's size, so growing one fails the
BUILD with the remedy in the message rather than corrupting a kit at runtime.
Verified by appending a probe field to EngineApiJobsV1 and watching it fire.

input and assets sit at v2 because they grew IN PLACE before this rule existed.
Their layouts are frozen from here; a version bump now means the semantics were
clarified, never that the struct grew.

── the test is the promise, executed ───────────────────────────────────────
api_abi_compat_test declares the table's pre-jobs shape (656 bytes) and views
the live 760-byte table through it, literally a kit built last week meeting
today's engine. core.logInfo, assets.loadMesh, nav.findPath and draw.drawLine
all resolve identically.

It also pins every group's OFFSET, not just its size: a reorder keeps every
size intact and still breaks every kit, so the build-time asserts cannot catch
it alone.

── what this does not do ───────────────────────────────────────────────────
It does not retroactively save existing kits. The ">=" logic lives in the
MODULE's copy of the shim, so a kit gains the protection only once rebuilt
against this header. One last mandatory rebuild, which is the argument for
landing it before any third party ships a kit, not after.
