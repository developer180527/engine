scene: load was O(n^2): a full ECS query per entity created

Sampling a --frames 1 load of a 50 000-object scene put 97.6% of the entire 22
seconds in one place:

  main -> SceneSerializer::loadAsync
    -> EntitySerde::createEntity            9075 / 9294 samples
      -> findById(flecs::world&, uint64_t)  9045      <- entity_id_util.h:47
        -> flecs::iterable<EntityId>::each  9033

createEntity called findById PER ENTITY as an id-collision check, and findById is a
full ECS query over every entity carrying EntityId. Creating entity k scanned the k
already created, n x O(n). findById's own comment said 'used by load (one pass)', and
that assumption was the bug. scene_service.cpp's cooked-scene loader had the same
pattern, and ironically already built an id -> entity map as it went without using it
for the check.

FIXED with EntityIdIndex (core/entity_id_util.h): one query up front, then O(1)
lookups. Two properties the per-entity scan gave for free and a naive map would lose,
it is seeded from the world so pre-existing entities still collide, AND inserted into
as entities are created so ids assigned within one load collide with each other too.
Threaded through SerdeContext::idIndex and used by all three loaders (JSON disk,
memory snapshot, cooked binary); createEntity keeps findById as the fallback when no
index is supplied, so one-off callers like undo are unaffected.

  objects   load before   after    ms/entity before  after
   10 000   2.4 s         1.52 s   0.24              0.152
   25 000   7.0 s         2.92 s   0.28              0.117
   40 000   14.8 s        4.17 s   0.37              0.104
   50 000   22.0 s        4.78 s   0.44              0.096

4.6x at 50 000, and THE SHAPE IS THE PROOF: per-entity cost went from doubling across
the range to flat-and-improving as fixed costs amortise. A quadratic term that
disappears is a stronger result than a number that merely got smaller. What remains is
~0.1 ms per entity of genuinely linear work, nlohmann still materialises the whole
27 MB document before the first entity exists, but that no longer limits scene size.

AN ANOMALY SURVIVED, AND I DESTROYED THE ARTIFACT. One specific generated scene loads
pathologically (>150 s) and still did after this fix. Ruled out: size (25 000 loads in
2.92 s elsewhere), hierarchy (0% vs 15% children, 6.94 vs 7.04 s), the project
directory, project.json, and a stale SQLite WAL, the DB is identical in shape to a
healthy project's. Swapping a healthy scene file into that same directory loads in
2.77 s, localising it to that one scene FILE. I then overwrote the file during that
very test, so it cannot be diagnosed. Careless: the test should have copied the suspect
aside first. Noted in issues.md so it is kept if it recurs.
