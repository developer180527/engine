mem: a navmesh that allocated through malloc, and the first test that any library is routed

Ten vendored libraries are supposed to allocate through engine_core. Nine do.
Recast and Detour never had their hooks called, zero call sites for
rcAllocSetCustom or dtAllocSetCustom anywhere in the tree, so every bake put
231 allocations and ~82 KB outside the engine entirely: off the tagged TLSF
heaps, absent from the census, uncounted against the budget the census exists to
enforce.

`DetourAlloc.cpp` is literally `return malloc(size)`.

── WHY THIS WAS WORTH FIXING RATHER THAN NOTING ────────────────────────────
It is RUNTIME, not bake time. dtAllocNavMesh and dtAllocNavMeshQuery run at load
and dtNavMeshQuery::init allocates its node pools there, and the whole path is
exposed to Kits through the FROZEN API table as EngineApiNavV1. A Kit calling
pathfinding was allocating engine data through libc while every other subsystem
went through mem::.

The shape of the defect is not a wrong decision, it is an absent one, in the one
library nobody went back to.

── THE FIRST TEST OF ANY LIBRARY'S ROUTING ─────────────────────────────────
This is the part that generalises. src/core/memory/info.md carries a table of ten
libraries and the hook each is wired through, and it was a claim in a document
with NOTHING BEHIND IT. mem_test exercises the MEM_SCOPE mechanism; it never
asserted that a Jolt allocation lands on the Physics tag, or a flecs one on ECS.

Which is exactly how this survived. Nine libraries were routed, the tenth was
not, and no check in the repo could tell the difference.

nav_test now asserts the bake lands on Tag::Nav, 231 allocations, 82344 bytes,
with a `> 1024` floor as well, so a hook that fired for one incidental structure
while missing the navmesh would not pass. Mutation: removing
installNavAllocators() yields "0 allocations on Tag::Nav" and three failures.

The other nine remain untested and that is now written down in the table itself
and filed as an open item, rather than left as an implication of the table
looking complete.

── Tag::Nav, AND WHY ADDING A TAG IS SAFE ──────────────────────────────────
EngineApiMemoryV1 passes `uint8_t tag`, and its own comment says an unknown tag
is charged to the general one "so a kit built against a newer tag list still runs
on an older host", the list is designed to grow. Every internal use is a
Tag::Count-sized loop, not a frozen array; checked before adding.

kTagNames is constexpr now with a static_assert that the last entry is non-null.
Adding a tag and forgetting its name previously produced a zero-initialised entry
— tagName() returning an empty string and a BLANK CENSUS ROW rather than a
failure. Mutation-verified: an unnamed tag now fails the build with that message.

The hooks install through a function-local static, so exactly once and never
after allocations already exist, a later swap would hand pointers from one
allocator to another's free(). Alignment is alignof(max_align_t) because neither
library takes an alignment parameter, so it is asking for malloc's guarantee and
must get at least it (BUG-0028 is what under-promising there costs).

── GLFW AND SDL3: DEFERRED AS ONE ITEM, NOT HALF DONE ──────────────────────
Both window backends allocate outside the engine. GLFW is vendored at 3.5 and has
glfwInitAllocator; SDL3 has SDL_SetMemoryFunctions. Neither is wired.

Not fixed here, and the reason is not that GLFW is legacy, ENGINE_WINDOW_BACKEND
still defaults to `glfw`, described in CMakeLists as "default, complete" against
sdl3's "in progress". Fixing GLFW alone would leave the identical hole for the
backend meant to replace it. Both allocate at init and window creation rather than
per frame, so the volume is low and bounded, which is the honest reason it is
deferred rather than urgent. Recorded with a trigger.

── THREADING: AUDITED, NOTHING TO DO ───────────────────────────────────────
Checked alongside, since "everything managed by engine_core" is two claims. Jolt
runs on the engine worker pool through JoltJobsAdapter, JobSystemWithBarrier
minus the threads, installed at jolt_plugin.h:134. bgfx's render thread is
suppressed by calling renderFrame() before init. flecs never calls ecs_set_threads.
ozz's thread-creating files are all under extern/ and samples/, none in the
library. miniaudio owns its device thread, which is correct by design:
provider-abi.md rule 1 gives the provider its resource, its threads and its
schedule.

ctest -L unit 58/58. engine_doctor 76 docs, 0 errors. Three hardened docs
re-verified and bumped, core, core/memory and runtime, after checking that
neither core/info.md nor runtime/info.md enumerates the tag list.
